## Approaches considered

1. **A library** (svelte-i18n MIT, typesafe-i18n MIT, Paraglide Apache-2.0, i18next MIT). All are
   clearly licensed, but each brings its own message syntax or compiler, a runtime of 5–30 kB, and a
   catalogue format Android does not read; svelte-i18n pulls `intl-messageformat` (full ICU incl.
   `select`, nested plurals, number skeletons) which has no one-to-one Android mapping.
2. **In-house, ICU subset on `Intl`** (chosen). The browser (and Android, and Go via x/text which the
   server already depends on) has plural rules; what is left is a ~150-line parser/formatter for a
   deliberately small syntax that converts one-to-one to Android `strings.xml`/`<plurals>`.
3. **Android XML as the master format**, web generated from it. Rejected: the web is the only client
   today and owns all strings; XML is hostile to review diffs.

- Ruling: in-house formatter on `Intl.PluralRules`/`NumberFormat`/`DateTimeFormat`, no i18n dependency —
  the needed syntax is small, a library's richer syntax would be the part Android cannot share, and
  nothing new ships under a third-party licence — cost if wrong: we maintain ~300 lines (parser, formatter,
  negotiation, converter) and their fixtures; switching to a library later means converting syntax.
- Ruling: no Sources-page credit is added because no i18n code ships; `thirdPartyLicenses.test.ts` stays
  unchanged and the Sources page gains no row — cost if wrong: none (if a library is adopted later, its
  credit and licence test are added then).

## Catalogue format and key scheme (contract `docs/contracts/i18n/`)

**File layout.** One flat JSON object per language: `apps/web/src/lib/i18n/messages/<lang>.json`
(`en.json` only for now), keys sorted, values strings. Optional translator notes in
`messages/notes.json` (`key → note`, English, never shown). The server's mail catalogue is a second file
set of the same format, `server/internal/mail/messages/<lang>.json`, keys under `mail.*` only.

- Ruling: one file per language, not per feature — a translator (and the Android converter) works on one
  file; per-feature files multiply by languages and break lazy loading of a language into many requests;
  sorted keys keep merge conflicts local — cost if wrong: a big `en.json` (~150 kB raw, ~35 kB gzip) in
  the main bundle; splitting later is a mechanical move because keys are already namespaced.
- Ruling: the web catalogue is the source of truth for every client key; Android converts `en.json` (and
  later languages) with the documented converter and adds Android-only keys under `android.*` in its own
  file — cost if wrong: Android-only strings live elsewhere; acceptable, they have no web meaning.

**Keys.** `area.part.name` — 2 to 6 dot-separated segments, each `[a-z][a-zA-Z0-9]*` (lower camelCase, no
`_`, no `-`), at most 120 characters. The first segment is one of a closed list kept in the contract
README: `app, nav, common, auth, account, search, entry, study, flashcards, reader, journal, grammar,
stats, weekly, goals, notes, lookups, settings, admin, sources, packs, pwa, widgets, plugin, apiError,
format, features, milestones` (the list test pins it; Task 0 may add one for what item 6 or 7 brings).
Adaptation: `features` (the core features' names, the switched-off notice, Settings → Features) and `milestones`
(item 7) added; item 5's package lines and stroke packs go under `packs`, its sync and download errors under
`apiError`, the Sources stroke section under `sources`, the logo link under `nav`. Example:
`settings.account.interfaceLanguage.label`.

- Ruling: segments are camelCase without `_` so the Android name `segments.join('_')`
  (`settings_account_interfaceLanguage_label`, a valid resource name) is collision-free and reversible —
  cost if wrong: none found; a key that needs a digit-leading segment cannot exist.
- Ruling: a key is **stable and never reused**: changing a message's meaning means a new key; a removed
  key is appended to `docs/contracts/i18n/retired-keys.json` and a test fails if a catalogue key is
  retired — so a stale Android or translation file can never show a wrong sentence — cost if wrong: a
  slowly growing retired list.
- Ruling: `common.*` holds only context-free UI words (`common.action.save`, `.cancel`, `.close`,
  `.delete`, `.retry`); every sentence or label with context gets its own key even if the English text
  repeats — languages differ where English does not — cost if wrong: duplicate English values (a test
  does not flag duplicates).

**Message syntax (ICU subset).** A message is literal text with:
- `{name}` — an argument, `name` = `[a-z][a-zA-Z0-9]*`, inserted as a string (callers pre-format numbers
  and dates with the locale helpers below).
- a plural: the **whole** message is `{name, plural, one {…} other {…}}` with any of the CLDR categories
  `zero one two few many other` (`other` required); inside a branch `#` is the argument formatted with
  `Intl.NumberFormat(locale)` and `{other}` arguments may appear.
- `<tag>…</tag>` — a rich-text span, `tag` = `[a-z][a-zA-Z0-9]*`, no attributes, no nesting, rendered by
  the caller (a link, `<strong>`).
- `'` is a literal apostrophe (no ICU quoting); a literal `{`, `}`, `<` or `#` outside a plural branch
  is invalid (pass it as an argument).

- Ruling: no `select`, no `=N` exact matches, no nested or partial plurals, no number/date argument types
  — each has no one-to-one Android form (`<plurals>` must be the whole string and has no exact matches;
  `zero` is a CLDR category, not "0"); "no items" states get their own key — cost if wrong: a few more
  keys and call-site `if`s than full ICU.
- Ruling: plain apostrophes, not ICU quoting — English UI copy is full of "don't"/"isn't" and ICU's
  doubling rule is the classic source of broken strings; the converter escapes for Android — cost if
  wrong: a message can never show a literal `{` (none does today).
- Ruling: a missing key in a non-English catalogue falls back to `en` per key (dev/test log a warning);
  a missing argument throws in dev and tests and renders `{name}` in production — a half-translated
  language is still usable, tests catch real mistakes — cost if wrong: mixed-language screens while a
  translation is incomplete (the catalogue test reports coverage per language).

**Android converter rule** (normative in the README, reference implementation
`apps/web/scripts/i18n-android.mjs`, fixture `android-convert.json`): key → name `join('_')`; plain
message → `<string name>`; plural → `<plurals name>` with one `<item quantity>` per category and `#` →
`%1$s` (the formatted count is always format argument 1); other arguments take positions in the order
of first appearance in the **English** message (`{a}` → `%N$s`, after the count in a plural), identical
for every language; XML-escape
`& < >`, escape `' " \` with `\`, `%` → `%%`, a leading `@`/`?` with `\`; `<tag>…</tag>` →
`<annotation tag="tag">…</annotation>`; notes become `<!-- … -->` above the item.

## Web runtime

`$lib/i18n` exports:
- `t(key: MessageKey, args?: Record<string, string | number>): string` — a plain function reading the
  active catalogue; `MessageKey = keyof typeof en` from the JSON import, so `svelte-check` rejects an
  unknown key at compile time without a generator.
- `<Msg key args>` with Svelte 5 snippets named after the message's tags for rich text.
- `locale` (the resolved interface language), `formatLocale` (below), `setInterfaceLanguage()`.

- Ruling: `t` is a plain function, not a store, and changing the interface language reloads the page —
  language changes are rare, and a store would make every string reactive and every component
  subscribe — cost if wrong: one reload on change (the PWA shell is cached, so it is fast).
- Ruling: argument names are not type-generated; the catalogue test checks every literal call site
  `t('k', { … })` it can parse against the message's arguments, and a missing argument throws in tests
  — no build step — cost if wrong: an unparsed dynamic call site is checked only at runtime.
- Ruling: dynamic keys (`t(\`x.${y}\`)`) are forbidden by a lint; enumerations use typed maps
  (`Record<SettingsTab, MessageKey>`), so every key appears as a literal and the unused-key check stays
  exact — cost if wrong: a few more lines per enumeration.
- Non-English catalogues load lazily (`import.meta.glob('./messages/*.json')`) before the app mounts
  (root `+layout.ts`); `en` is imported eagerly.

**Catalogue tests** (`lib/i18n/catalogue.test.ts`): every key matches the scheme and the area list;
every message parses; every non-`en` key exists in `en` with the same argument set, tag set and
plural-ness, and its plural has exactly the categories of `Intl.PluralRules(lang)`; every key in `en` is
used as a literal in non-test `src/` (or in the built-in manifest key map); every literal `t('…')` key
exists; no key is retired.

## Extracting the existing strings

Per area, one mechanical commit: move strings to `en.json`, replace them with `t()`/`<Msg>`; no wording
change, no logic change. The existing DOM and unit tests assert English text and **stay as they are** —
they now also verify the catalogue (a wrong key or a wrong text fails them). Pure TS view modules return
`t(...)` results; their unit tests are unchanged.

- Ruling: extraction does not reword anything, even awkward copy — the diff must be reviewable as a
  move; rewording is a separate commit with its own test change — cost if wrong: known-awkward English
  survives into the catalogue (translators can ask).
- Ruling: hand-rolled plurals become catalogue plurals in the same area commit (that changes only
  generated text where the old code was wrong, e.g. "1 hour" cases); each such case gets a unit test —
  cost if wrong: small, the tests pin it.

**Lint against new hard-coded strings** (`lib/i18n/hardcoded.test.ts`, heuristic): in every non-test
`.svelte` file (markup only, `<script>`/`<style>` stripped) a text node or an `aria-label`, `title`,
`placeholder`, `alt`, `label` attribute value with two or more letters fails, unless allowlisted in
`lib/i18n/allowlist.json` (`{file, text, reason}`; e.g. "qinqin", sample CJK in a demo, `·`). In non-test
`.ts` under `src/lib` and `src/routes`, a string literal that looks like a sentence (starts with a capital
letter, contains a space, ≥ 2 words) fails unless it is a log/`Error` argument or allowlisted. During
extraction a `pending.json` baseline lists not-yet-extracted files; each area commit removes its files;
the last task deletes the baseline. A second lint fails on `Intl.*Format(`, `toLocale*String(` and
`Intl.PluralRules(` outside `lib/i18n/` unless allowlisted with a reason (`studyDay.ts`, `zoneSettings.ts`).

- Ruling: heuristic lint with an explicit allowlist, not an AST analysis — catches the common case (a
  literal in markup) at near-zero cost; the allowlist is reviewed in diffs — cost if wrong: an odd
  construct (a string in a `{#if}` ternary in markup, `{'Text'}`) escapes; the TS rule and the pseudo-
  locale test below cover part of it.
- Ruling: a test-only pseudo-locale (`en-XA`: every message wrapped and accented) renders a sample of
  page components and asserts no plain ASCII English text node remains — it finds concatenation and
  missed strings the heuristic cannot; it is generated in the test, never shipped (not a translation) —
  cost if wrong: maintenance of the sample list.

## Interface language setting

**Stored on the server, per user**: column `users.interface_language TEXT NOT NULL DEFAULT ''`
(`''` = follow the browser/device). Read in `GET /api/auth/me` as `interfaceLanguage`; written by
`PUT /api/me/interface-language {language}` → `200 {language}`; 422 `invalid_language` when the value is
neither `''` nor a tag matching `^[a-z]{2,3}(-[A-Z][a-z]{3})?(-([A-Z]{2}|[0-9]{3}))?$` (canonical case).
Route row: `accUser`, token rule `noTok`, not cacheable by the service worker; restricted sessions are
refused like every other route. Adaptation: the migration is the next free number when Task 24 runs — 040 today
(`039_packages.sql` is the last; item 7 adds none; if item 6 took 040, the next one); the `route{}` row sits next
to `PUT /api/me/time-zone` (`accUser`, `noTok`), with 401 and two-user isolation tests, the PWA route fixture
regenerated with `UPDATE_ROUTES_FIXTURE=1` and `node scripts/gen-api-docs.mjs` run. It is no admin action, so it is
not in item 1's re-authentication table (`auth/README.md`). Backup: `account.json` gains optional `interfaceLanguage`
(`formatVersion` stays 1; an absent key leaves the setting unchanged on restore).

- Ruling: a server-side user setting, not a sync row — the server must know it for mails sent before
  sign-in (reset, sign-in code), a sync row is workspace data the server does not interpret; Android
  reads it from `me` like every account setting — cost if wrong: one migration, one route.
- Ruling: the server validates syntax only, not support — a newer Android with more languages can store
  its choice and the web falls back per the negotiation rule — cost if wrong: a stored tag no client
  supports behaves like `''` plus the user's chosen base language where possible.
- Ruling: `noTok` — a script has no reason to change the interface language — cost if wrong: none.

**Resolution** (contract rule, fixture `negotiate.json`, implemented in TS and Go): candidates = the
stored setting if non-empty, else `navigator.languages` (web), the device list (Android), or
`Accept-Language` by q-value (server). For each candidate in order: exact match (case-insensitive) in
the supported list; then drop trailing subtags one at a time; `zh-TW`, `zh-HK`, `zh-MO` imply `zh-Hant`,
other `zh` imply `zh-Hans` before truncation. First hit wins; no hit → `en`. Today the supported list is
`["en"]`, so everything resolves to `en`.

- Ruling: a small written algorithm in both languages instead of x/text `language.Matcher` or a browser
  API — three clients must agree exactly and fixtures can pin a 15-line rule, not a matcher's distance
  tables — cost if wrong: weaker matches for exotic tags (`nb` vs `no`), fixable by aliases.

**Formatting locale.** Dates and numbers use the interface language plus the region of the first
browser language with the same primary subtag (`en` + `navigator.languages[0] = en-GB` → `en-GB`); else
the interface language. With Intl unable to resolve it, `en`.

- Ruling: keep the device region for formatting — an English UI user in Germany or Britain expects
  their own date order; the server stores only the language — cost if wrong: two devices of one user may
  format dates differently (correct for each device).

**Web flow.** Signed out: resolution from `navigator.languages`. Signed in: `me.interfaceLanguage`.
The last resolved language is mirrored in `localStorage` (`qq.interfaceLanguage`) for the first paint
and offline start; the server value wins when `me` loads (reload only if it differs). Settings →
Account gets "Interface language": "Browser default (English)" plus each supported language by its own
name (`Intl.DisplayNames([lang])`); saving reloads.

## Server-side text

- Ruling: the API `message` stays an English sentence for developers and logs; clients show text from
  their catalogue by `error` code (`apiError.<code camelCased>`), with context overrides where wording
  differs (`auth.login.error.rateLimited`); `authErrors.ts` stops reading and parsing `message`; an
  unknown code (newer server) shows `apiError.unknown` ("Something went wrong ({code}).") — clients
  already must branch on codes, and a server cannot know the client's catalogue — cost if wrong: a new
  server code shows the generic text until the client adds a key (a test pins that every code in
  `auth/errors.json` and the area READMEs has a key). Adaptation: that includes item 4's
  `study_row_invalid` and item 5's `sync_collection_moved`, `sync_page_invalid`, `sync_cursor_expired`,
  `package_not_found`, `package_revision_gone`, `download_busy` (429, "another package download is running").
- Ruling: `Error`s a client throws for developers (`sync/pager.ts` "a page does not match the contract",
  `maxPages`) stay English and are never shown; the UI shows a catalogue text for "sync failed" instead, and a
  user-facing client error (`PartialPushError` "rows were not written …") becomes a catalogue plural — the lint's
  `Error`-argument exemption must therefore not hide user-facing texts: an `Error` whose `message` is rendered
  (`errorMessage(err, …)`) is extracted — cost if wrong: an English developer message could reach the screen;
  the pseudo-locale sample of each area catches it.
- Ruling: mails are localised by the user's language: stored setting if set, else the triggering
  request's `Accept-Language`, else `en`, negotiated against the languages present in
  `server/internal/mail/messages/`; subjects and bodies move into that catalogue (`mail.reset.subject`,
  `mail.reset.body`, …) in the shared syntax, formatted by a small Go implementation of the same subset
  (plural categories from `golang.org/x/text/feature/plural`, already a dependency, BSD-3) and checked
  against the same fixtures — mails reach people who cannot read English, and one syntax for both sides
  keeps translators on one format — cost if wrong: a Go formatter to keep in step with TS (fixtures pin
  both). The "within 1 hour" plural is fixed by the catalogue plural.
- Adaptation (item 4): flashcards and the reader are core features with reserved ids; their nav/page names come
  from `coreFeatures` (`title` "Decks"/"Reader", `label` + `verb` "Flashcards are"/"The reader is"), not from the
  manifest. Ruling: `label` + `verb` are replaced by one whole message per feature
  (`features.flashcards.switchedOff`, `features.reader.switchedOff`) through a typed map — a label glued to a
  verb cannot be translated — cost if wrong: none.
- Ruling: plugin manifests: built-in plugins' `name`, `description` and activity `label`/`describe` are
  looked up as `plugin.<id camelCased>.*` with the manifest text as fallback; third-party manifest text is
  shown verbatim (no translation, no `lang` override) and manifest localisation is a follow-up (sdk 2) —
  the sdk 1 contract cannot change in this item — cost if wrong: third-party plugins stay English.
- Ruling: pack names, licence text, attribution and book metadata are data, never translated; they keep
  the `lang` the data declares (`cjkLang`) — cost if wrong: none.
- Ruling: `manifest.webmanifest` stays English (one static file) — cost if wrong: an English install
  name on a non-English device; revisit with a second language.

## Contract `docs/contracts/i18n/`

README (key scheme, area list, catalogue format, syntax, fallback, converter rule, negotiation rule,
formatting-locale rule, setting route, what is never localised) and fixtures: `messages.json` (message,
locale, args → output, incl. plurals for `en`, `fr`, `ru`, `ar`, `ja` with test-only messages),
`invalid-messages.json` (message → error kind), `plural-categories.json` (locale, n → category),
`negotiate.json`, `language-tags.json` (setting validation), `android-convert.json`,
`retired-keys.json`, `interface-language-api.json` (route shapes). Web tests decode all; Go decodes
`messages.json`, `plural-categories.json`, `negotiate.json`, `language-tags.json`,
`interface-language-api.json`. `overview.md` gets an "Interface language" section; `README.md` the
folder row; `auth/errors.json` the `invalid_language` code; `auth/me.json` the field.

- Ruling: plural fixtures are limited to integers where CLDR versions agree (0–25, 100, 101, 1000000)
  and to the six locales above; a locale where Node's ICU and x/text disagree is dropped and recorded —
  cost if wrong: thinner cross-implementation coverage.

## Out of scope

A second interface language and its translation (needs a human translator); RTL layout audit; plugin
manifest localisation (sdk 2); localised `manifest.webmanifest`; server-rendered HTML (there is none).
