# #285 — a larger writing pad on phones (2026-11-27)

Milestone v0.9.0, phase 2. Branch `feature/v090-285-larger-pad` (from `feature/v0.9.0`).

## What

The writing pad is fixed at 200 px (`SIZE = 200` in `WritingCard.svelte` and `ScriptsWritePad.svelte`). On a
phone it should take about the full content width, square, but never so tall that the prompt, the feedback line
and the docked actions leave the screen; desktop keeps about today's size. Both pads (flashcards' writing card and
the scripts trainer's Write mode) share one rule. Strokes are matched in pad units already (`toPadUnit` divides by
the pad's box), so the matcher's tolerance does not change with the size; the ink's line width follows the pad.

## The rule

`side = min(width, max(minSide, min(maxSide, side + slack)))`, rounded down, where

- `width` is the width the pad's container gives it (the pad is never wider: no sideways scroll);
- `slack` is how far the last thing that must stay visible (the feedback line on a card, the Hint / Show row in the
  scripts trainer) ends above the free space's bottom edge (the viewport's height minus the docked actions), at the
  top of the page: positive means room to grow, negative means the pad must shrink. Measured in the scroll
  container's content coordinates, so it does not depend on where the page is scrolled;
- `minSide` = 10rem (160 px): below that a character cannot be drawn; a landscape phone scrolls instead;
- `maxSide` = 22.5rem (360 px) on a touch screen (`pointer: coarse`), 17.5rem (280 px) with a mouse or pen
  (`pointer: fine`).

It is re-measured when the container's size or the window's size changes (rotation, a resized window, the browser
bar), and the pad's canvas follows through its own `ResizeObserver`, mid-card included.

## Rulings

- Ruling: the pad is sized by measurement (a small action), not by a CSS formula — the study face only has a
  minimum height, so CSS cannot know the height left over below the prompt; a fixed `100dvh - Xrem` reserve would be
  wrong whenever the prompt wraps onto a second line — cost if wrong: a little layout code; the pure part is
  unit-tested and the measurement is pinned by the e2e.
- Ruling: slack is measured once per size change, relative to the pad's current side, so one pass reaches the fixed
  point (layout below the pad does not depend on its size) — cost if wrong: a second resize callback that changes
  nothing.
- Ruling: the docked actions are reserved at their height when the pad is measured (Show strokes); the grade bar
  that replaces it after the answer does not shrink a finished pad — a pad that jumps after the last stroke would be
  worse than a dock that covers the answer's first line, which scrolls into view — cost if wrong: on a short phone the
  grade bar may cover part of the answer until the learner scrolls, as today.
- Ruling: `maxSide` 22.5rem on touch screens and 17.5rem with a fine pointer — the issue asks for "today's size, or a
  little larger" on desktop; a mouse gains nothing from a large pad, a finger does; 22.5rem lets a 360–400 px phone
  use its whole content width — cost if wrong: two numbers in `padLimits`.
- Ruling: `minSide` 10rem, and below it the page scrolls — a landscape phone (360 px tall) cannot fit a usable pad
  and the prompt; a pad smaller than 160 px is too small to draw on — cost if wrong: in landscape the feedback line
  is below the fold until the learner scrolls.
- Ruling: the ink's line width is 3 % of the pad's side (6 px at 200 px, as today), at least 4 px — a 6 px line on a
  328 px pad looks thin, and a stroke's look should not change with the device — cost if wrong: cosmetic.
- Ruling: `.visually-hidden` (app.css) loses its `margin: -1px` — the study session's polite "graded" line sat at
  [-1, 0] and failed the 360 px guard (the session screen was not in #296's spec); a 1 px absolute box needs no
  negative margin — cost if wrong: none seen; the element stays 1 px, clipped and absolute.
- Ruling: the e2e routes `/hanzi/` (Hanzi Writer data from the web app's own dev dependency) and adds `writing` to
  the eligibility answer, and blocks the service worker in that spec — the e2e server has an empty pack root, and
  `page.route` does not see what the app's service worker fetches (its `/hanzi/` cache); the first runs failed
  intermittently with "Nothing to study" for exactly that reason — cost if wrong: the spec does not cover the
  server's real stroke route (covered by the Go tests and contract).
- Ruling: at 360 × 740 the pad is height-bound (about 260 px with the reading hint shown): the prompt, readings and
  gloss leave less height than width; at 360 × 860 it fills the content width (328 px). Both are pinned — the issue
  puts the dock and the feedback line first — cost if wrong: a 740 px phone gets 260 px instead of 328 px.
- Ruling: the limits are in rem (read from the root font size) so a larger font gives a larger pad — cost if wrong:
  none; the pad is still never wider than its container.
