## Rulings (decided by the assistant; the owner said "let's do the follow-ups")

- **A.** The endpoint returns, per level in `ord` order, the set of Han characters for the level exactly as the server derives them for badges (word-unit schemes: every Han character of each member word, lowest level wins; character-unit schemes: the characters themselves), as `{"levels":[{"id":N,"name":"…","chars":"日本…"}]}` (chars as one string, deduped, code-point order stable by first appearance). Public like `/api/schemes`; weak ETag from the scheme's max `updated_at` + member count; gzip like `/api/characters`. The web map uses it for ALL scheme groupings (word and character units), removing `/api/schemes/{id}/entries` + `schemeCharMembers` from the map path (keep the helper only if still used elsewhere; delete if dead).
- **B.** Deleting a workspace removes everything scoped to it in one transaction: `study_events`, `plugin_data` rows of that workspace, `library_books` rows (+ their bookmarks and highlights; content files `<data>/books/<user>/<id>.json` removed after commit), and the workspace row. **The user's last workspace cannot be deleted** (409 "keep at least one workspace"; otherwise default-workspace creation would silently resurrect all languages). Only the owner can delete (404 for others). Response 204. The web Settings page gets a Delete action with a confirmation dialog that states what will be removed (counts of books, cards, reviews — fetched or estimated from the data the app already loads; if counts are costly, show a generic list) and requires typing the workspace's label; the header selection falls back to another workspace; localStorage keys scoped to the deleted workspace id (study setup, remembered card types, ineligible memory, rail state per book etc.) are cleaned best-effort. Sync: clients that still hold plugin data for the deleted workspace must not resurrect it — check how push/pull behave for a workspace that no longer exists (push must be rejected with 404/403, pull must not list it) and test it.
- **C.** New cards get deterministic ids: `c-<kind>-<entryId>` for `vocab`/`writing`/`tone` and `c-sentence-<entryId>` for the single sentence card per word (the one-sentence-per-word ruling), so two devices that create the same card in the same moment write the SAME plugin-data key (last-write-wins merges them). Existing ULID cards keep their ids; `addCard` still dedupes by `cardKey` against what it can see. Additionally a pure `canonicalCards(cards, reviews)` step in `loadStudyData` consumers (queue building, mastery, widget counts, summary) merges existing duplicates: per `cardKey` the earliest-created card survives; reviews of the duplicates are re-pointed to the survivor in memory (never rewriting stored data); duplicates are not shown or counted twice. No server change.
- **D.** `PhoneticKey` additionally folds kunrei-shiki/Nihon-shiki spellings to Hepburn (si→shi, ti→chi, tu→tsu, hu→fu, zi→ji, sya/syu/syo→sha/shu/sho, tya/tyu/tyo→cha/chu/cho, zya/zyu/zyo→ja/ju/jo, di→ji, du→zu, wo→o, plus `n'`/`nn` handling stays) and treats the standalone tokens `wa`→`ha` and `e`→`he` and `o`→(wo/を stays o) in queries as the particles (は reads `ha`, へ reads `he` in the catalog readings); minimum phonetic length stays 3 folded characters. Gutenberg ja titles are out of scope.
- **E.** One read-only whole-branch review (most capable model) of `602ecf6..develop` focusing on cross-task integration, with one fix wave afterwards for Important findings.
- Not doable here: real screen reader and touch-device testing (state this in the final report).
