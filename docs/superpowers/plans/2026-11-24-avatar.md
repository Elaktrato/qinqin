# Plan — profile picture upload (avatar) (#189)

Issue #189 (phase 3 of #190), built as a core account feature (record
[0006](../../architecture/0006-core-features-instead-of-code-plugins.md): no plugin, no feature switch — a profile
picture is part of the account, like the email). Branch `feature/189-avatar` from `develop` at 2422f03b, worktree
`.claude/worktrees/189-avatar`. Test-first, one commit per task, the suites green after each. Go gates under
`flock /tmp/qinqin-go.lock`; the e2e suite (record 0007) at the end, three runs.

## What exists today

- The avatar is the first letter of the username in a tinted circle (`apps/web/src/lib/frame/Avatar.svelte`),
  shown only by the account menu (`AccountMenu.svelte`: the trigger at size `m`, the menu header at `l`), which
  the top bar, the navigation drawer, the phone bar and the restricted layout all mount. The admin user list shows
  no avatar.
- Journal photos (`server/internal/journal/image.go`, `photos.go`) are the pattern for image files: the type is
  sniffed from the content, `image.DecodeConfig` checks the size before any pixel is decoded, the picture is
  re-encoded as a JPEG (metadata gone), files live in `<data>/journal/<userId>/` (0600, dirs 0700). They are
  drafts: never backed up. `golang.org/x/image` (draw, webp) is already a direct dependency.
- The bearer token is the only credential (no cookie), so an `<img src="/api/...">` cannot authenticate: the web
  fetches protected images with `apiBlob` and shows an object URL (journal photos, audio clips through the
  session's `ClipCache`).
- Personal backup format 2 (`server/internal/backup`) is a zip of fixed names; the server backup is a tar of
  `qinqin.db`, `books/`, `packs/`, `audio/` only — it does NOT cover the rest of the data folder, so the avatar
  files need adding there.
- Account deletion and restore follow one registry (`server/internal/auth/delete.go`, `UserTables`, `UserDirs`).

## Design

**Server, `server/internal/imaging`** (new, moved out of the journal): `JPEGOrientation` (the EXIF orientation
reader) and `Orient` (applies it). The journal and the avatar both use them.

**Server, `server/internal/avatar`** (new domain package, a leaf: no `auth` import):

- `Normalize(data) (Images, error)`: sniff JPEG / PNG / WebP from the bytes (anything else, SVG and GIF included,
  is `ErrUnsupported`); refuse an animated picture before decoding (`ErrAnimated`: an APNG's `acTL` chunk before
  the first `IDAT`, a WebP `VP8X` with the animation flag or an `ANIM`/`ANMF` chunk); `DecodeConfig` first and
  refuse more than 8192 px a side or 25 megapixels (`ErrTooLarge`) before the full decode; decode; apply the
  EXIF orientation of a JPEG; flatten onto white; centre-crop to a square; scale to 256 and 64 px (CatmullRom)
  and encode each as a fresh JPEG (quality 85). The output carries no EXIF, no XMP, no ICC, no text chunk —
  nothing of the input but pixels.
- `Store{DB, Dir}` (`Dir` = `<data>/avatars`): table `user_avatars (user_id PK, hash, updated_at)` (migration
  050) and files `<Dir>/<userId>/<hash>-256.jpg`, `-64.jpg` (0600, dirs 0700). `hash` is the first 32 hex digits
  of the SHA-256 of the 256 px file, so a new picture has a new URL. `Set` writes the files, upserts the row and
  prunes the user's other files; `Remove`; `DeleteTx` (inside another transaction); `Current`; `Read(user, hash,
  size)` (only the current hash); `Prune`; `URL(user, hash)` = `/api/avatars/{userId}/{hash}`. Writers run under
  the users lock (`auth.Users.WithUserLock`), the lock account deletion and restore hold, so an upload never
  races a deletion or a restore of the same files.

**Routes** (rows of `routes()`, all `noTok`):

| Route | Access | Answer |
|---|---|---|
| `POST /api/account/avatar` (multipart field `file`) | user | 200 `{avatarUrl}`; 413 `photo_too_large` (over 5 MB, counted while reading), 415 `unsupported_image`, 415 `animated_image` (new), 422 `image_too_large`, 429 `rate_limited` (10 an hour) |
| `DELETE /api/account/avatar` | user | 204 (also when there is none) |
| `GET /api/avatars/{user}/{hash}[?size=64]` | user | the JPEG (256 px, or 64 px), `Cache-Control: private, no-cache`, `ETag`, `X-Content-Type-Options: nosniff`; 404 when that user has no picture with that hash; 400 for another size |
| `DELETE /api/admin/users/{id}/avatar` | admin | 204, audited `avatar_removed`; 404 when the user has none |

`GET /api/auth/me` and the admin user objects (`GET /api/admin/users`, `/{id}`, create, patch) carry
`avatarUrl` (string or null). Contract `docs/contracts/auth/avatar.json` (decoded by a Go test against the server
and a web test against the client code).

**Backups.** Personal archive: optional fixed entry `account/avatar.jpg` (the 256 px file), manifest count
`avatar` (0 or 1). Restore validates it with `Normalize` (never trusts the bytes), replaces the current picture
(an archive without one removes it, as restore replaces everything else) and prunes the old files after the
commit. Server backup: `avatars/` travels with the `db` part. Account deletion: `user_avatars` in the registry
(`PreviewKey avatar`), `avatars` in `UserDirs`.

**Web.**

- `lib/api/avatar.ts`: `uploadAvatar(blob)`, `removeAvatar()`, `removeUserAvatar(id)`, `avatarObjectUrl(cache,
  url)` through a new session cache (`AvatarCache`, object URLs revoked at the session's end, record 0009).
- `lib/frame/avatarImage.ts` (pure): which file a size needs at a device pixel ratio (`avatarSrc`).
- `Avatar.svelte`: an optional `src`; it loads through the session cache and shows the letter circle until the
  picture is there and again when it fails to load (`onerror`). Still decorative (`alt=""`, the surrounding
  control carries the name), except where it stands alone.
- `lib/account/avatarCrop.ts` (pure, tested): the square crop state — cover-fit, zoom 1–4× around a point, drag
  with clamping so the square is always covered, keyboard steps, the source rectangle to draw.
- `lib/account/ProfilePicture.svelte` (Settings → Account → Profile): choose a file (`<input type=file
  accept="image/jpeg,image/png,image/webp">`, which on Android offers the camera and the photo picker), crop
  (drag with mouse or touch through pointer events, wheel and a zoom slider, arrow keys and +/− on the focused
  crop area), save (a 512 px PNG drawn on a canvas is uploaded), replace, remove.
- The admin user list shows each user's picture (64 px file) and offers "Remove profile picture" for a user who
  has one; the audit list names `avatar_removed`.

## Rulings

- Ruling: the crop happens on the client (a canvas draws the chosen square at 512 px and the PNG is uploaded);
  the server still decodes and re-encodes whatever arrives and centre-crops anything not square — the upload is
  small whatever the camera, the browser applies the EXIF orientation when it decodes the picture, the server needs
  no crop parameters to validate, and a client without a crop (curl, a future app) still gets a sensible square —
  if wrong, a client that wants another crop has to crop itself, which costs nothing to add later as optional
  parameters.
- Ruling: the stored format is JPEG at quality 85, transparency flattened onto white — Go's standard library
  encodes JPEG and PNG only (`golang.org/x/image` has a WebP decoder but no encoder), and a photo as PNG is five to
  ten times larger; JPEG re-encoding is the journal's proven path — if wrong, a transparent logo shows on white,
  and moving to PNG is a change of the encoder and the file suffix.
- Ruling: no new dependency — `golang.org/x/image` (draw and webp) is already a direct dependency of
  `server/go.mod` for the journal; there is no vendor folder — if wrong, nothing: the module is pinned in
  `go.sum` like before.
- Ruling: the limits are 5 MB per upload (counted while the body is read, with `http.MaxBytesReader` and a
  limited part reader, never parsed to disk), 8192 px a side and 25 megapixels (checked with `DecodeConfig`
  before the decode, the journal's ceiling), two decodes at a time (the journal's decode slots are shared), and 10
  uploads per user and hour — a client-side crop sends about half a megabyte, so the caps only bite on
  hand-made requests — if wrong, a direct upload of a 50-megapixel camera file is refused with
  `image_too_large` and must be scaled first.
- Ruling: the picture is served by `GET /api/avatars/{user}/{hash}` to any signed-in user of the server (the
  issue: visible to signed-in users on the same server), with `Cache-Control: private, no-cache` and an `ETag`, not
  the audio clips' `immutable` — a browser revalidates each use, so a removed picture and a deleted account stop
  showing and an anonymous request is always a 401, while the content hash makes the revalidation a cheap 304 — if
  wrong, one extra request per picture and session.
- Ruling: the service worker does not cache the picture route (it stays `bypass`, the default) — the pictures are
  other users' personal data and the letter circle is a fine offline fallback — if wrong, an offline app shows
  letters instead of faces.
- Ruling: `avatarUrl` is in `me` and in the admin user object only; the `user` of the sign-in, register and reset
  answers stays as it is — the web loads `me` after every sign-in, and those answers describe the credential
  step — if wrong, a client that skips `me` shows the letter until it loads it.
- Ruling: the 64 px file is the same URL with `?size=64`; `avatarUrl` names the 256 px file — one URL per picture
  in the contract, and the client picks the file by the size it draws and the device pixel ratio
  (`avatarSrc`) — if wrong, a client that ignores the query shows the 256 px file everywhere (correct, larger).
- Ruling: the upload is `POST` multipart (field `file`) like the journal photos — the web's API client already
  sends `FormData` untouched, and the Android WebView's file input hands a `File` — if wrong, nothing: a raw body
  could be added.
- Ruling: errors reuse the journal photo codes (`photo_too_large` 413, `unsupported_image` 415,
  `image_too_large` 422; their meanings now name both routes) plus one new code `animated_image` (415) — an
  animated GIF is already `unsupported_image`, but an animated WebP or APNG is a JPEG/PNG/WebP the person chose, so
  "choose a JPEG, PNG or WebP" would read wrong — if wrong, one code more in the catalogue.
- Ruling: an administrator removes a picture without re-authenticating, audited as `avatar_removed` (actor, target,
  no detail) — it is moderation of content, takes nothing that cannot be uploaded again, and sits with the
  other non-destructive admin actions (sign out everywhere, require a password change) — if wrong, a stolen admin
  session can remove pictures, visible in the audit log.
- Ruling: the personal archive carries the 256 px file as the optional fixed entry `account/avatar.jpg` with the
  manifest count `avatar`; restore re-runs `Normalize` on it (the 64 px file is derived again) — the archive keeps
  the format version (an optional entry, like `interfaceLanguage`), and nothing in an archive is trusted — if
  wrong, a restored picture has lost one JPEG generation of quality.
- Ruling: a restore replaces the picture like every other part of the account data: an archive without one
  removes the current picture — the rule "restore replaces; there is no merging import" (`backup/README.md`) —
  if wrong, restoring an older archive takes the picture away and the person uploads it again.
- Ruling: the server backup carries `avatars/` with the `db` part, not as a fifth include name — the rows that name
  the files are in the database, and a database without its pictures (or pictures without the rows) is useless —
  if wrong, an administrator cannot leave the pictures out of a backup.
- Ruling: the picture is a core account setting, not a feature with a switch (record 0006) — it is part of the
  account like the email — if wrong, a switch is one row in `features/switches.json`.
