- One schedule replay per reviewed card per page load (`scheduleIndex`).
- Components thin; logic in tested pure modules. jsdom tests use `src/lib/testing/domSetup.ts` (Node 26 CI).
- Copy says "Young", never "Review", for the word state (spec ruling).

## Review Focus

1. **Idempotent add.** Adding the same level twice writes nothing the second time; adding on two
   "devices" (two plans from the same input) yields identical rows; a renamed copy keeps its name on
   re-add; a deleted copy is revived, not duplicated (Task 11 fixture).
2. **Numbers match the rest of the app.** A deck's studied/state counts equal `wordStateCounts` for that
   deck; mastered equals a hand count over `cardScore ≥ 80`; Due equals the home widget's `dueCounts`
   for the same deck (Task 2).
3. **Card management parity.** The deck detail and the `/study` Card manager use the same
   `cardActions` controller; undo after a partial failure, serialized writes and the move-undo
   liveness rule are pinned before the extraction (Task 4).
4. **Authorization of the new route.** 401 without a token; the body cap and id cap; nothing
   user-specific in the response (Task 5).
5. **Thousands of cards.** The counting test proves one replay per reviewed card; rows render in
   batches; system levels load only on expand (Tasks 2, 3, 12).
6. **Deleting a deck** moves its cards out first (existing `deleteDeck`) and tombstones `deckcfg:`; the
   confirm text names where the cards go (Task 9).
