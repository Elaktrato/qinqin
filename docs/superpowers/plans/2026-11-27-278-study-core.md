## Rulings

- Ruling: the core is `lib/studycore`, a new name, not `lib/study` kept for the core — the old name meant "flashcards
  and everything else"; a new name makes every stale path fail the unresolved-import guard and reads as what it is
  — a second rename if the owner prefers another name (mechanical, one script).
- Ruling: the core keeps the shapes and parsers of the card, deck, limit and FSRS rows (`types`, `canonical`,
  `deckSettings`, `limits`, `newOrder`, `fsrsParams`) — they are rows of the one study cache that every feature reads
  (the read model parses them; goals read the limits; stats read the decks) — some flashcard-shaped data sits in the
  core; splitting the read model by feature would be a behaviour-level change, not housekeeping.
- Ruling: the derived FSRS schedules (`scheduler.ts`) are core, the queue builder is flashcards (`session/queue.ts`)
  — mastery and known words derive from the schedules, and the drills framework gives each drill item its own FSRS
  schedule derived from events (v0.9.0 plan §3) — if drills need another replay, it is added beside `scheduleFor`.
- Ruling: `lib/exercises` holds cloze, word salad, tones and writing — the issue names cloze and word salad (grammar
  uses both); tones and writing are used by the visual aids, scripts and `lib/writing`, and the tone-pair drill
  (#180, #300) reuses the tone rules — a later drill that wants a different exercise shape adds its own module there.
- Ruling: `audioCue` goes to `lib/audio/cue.ts`, `strokeData`/`strokeIndex` to `lib/writing`, `starter.ts` to
  `lib/starter` — each is shared or owned outside flashcards (`lib/audio/button.ts` reads the card audio type; the
  entry page, scripts and the offline prepare read stroke data; Starter mode owns its stage rules) — none.
- Ruling: `commands/settings` (deck and workspace limits, FSRS sets) is flashcards; the settings pages import it as a
  feature's public piece (record 0004 allows that) — the drills will have their own settings; if they share the
  workspace limits, the command moves to the core.
- Ruling: the guard checks every file in `lib/studycore` and `lib/exercises`, tests included, against
  `lib/features/flashcards` and the flashcards routes — a core test that needs flashcards belongs with flashcards —
  none.
- Ruling: other features may still import flashcards' public pieces (record 0004 already allows it); the guard does
  not restrict them in this issue — the one-way rule the drills and courses need is "the core never imports
  flashcards"; restricting every feature is a wider change than this housekeeping issue.
- Ruling: no `NEXT.md` line — nothing user-visible changes.
