Date: 2026-11-16. Goal: get the web app and the server ready for the Android client (v0.4.0, issues
#34–#38). **No Android code. No merge to `main`, no tag, no release.** v0.3.0 is on `main`.

Read first: `README.md`, `docs/ROADMAP.md`, `docs/git-flow.md`, `docs/contracts/README.md`,
`docs/contracts/overview.md` (and its "Gaps"), the handoffs `2026-11-15-v0.3.0-handoff.md` and
`2026-11-16-v0.3.0-stretch-handoff.md`, and the issues below.

## Process (same as the v0.3.0 runs)

- Collection branch `feature/v0.4.0-prep` from `develop`; one topic branch per item
  (`feature/v040p-<name>`, its own git worktree), merged `--no-ff` into the collection branch; the
  collection branch is merged `--no-ff` into `develop` when an item is done, all gates are green, and CI
  on that `develop` commit is green. Never force-push or rewrite history.
- Per item: spec (`docs/superpowers/specs/`) → plan (`docs/superpowers/plans/`) → strictly test-first
  build, one commit per task → independent review on the strongest model (security focus for auth,
  tokens, files, sync) → one fix wave → mutation check of at least three new tests → merge.
- Every non-obvious decision: `Ruling: <what> — <why> — <cost if wrong>` in the spec or plan.
- Decision rule: licensing first (bundle nothing whose licence is unclear; credit on the Sources page),
  then the best UX even at higher development cost.
- Any rule a second client must follow gets a `docs/contracts/` folder with a README and JSON fixtures,
  decoded by Go and web tests. `docs/wiki/` and the README stay accurate (doc tests check them).
- New routes: a `route{}` row with the right access value **and a deliberate token rule** (personal
  access tokens, #83; the default is no tokens), authorization and two-user tests, the PWA route fixture
  (cacheability decided; default no), regenerated `docs/wiki/API-Routes.md`.
- No browser automation: unit tests, jsdom component tests (`*.dom.test.ts`), built servers driven by
  curl/Python. Everything that needs a human goes into the handoff.
- Issues: create one for every new item; close each with a short summary when its item is merged.
