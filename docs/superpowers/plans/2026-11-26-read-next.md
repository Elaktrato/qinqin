# "Read next" suggestions — plan (issue #183)

Overview: `docs/superpowers/specs/2026-11-26-v090-courses-overview.md` (track R, independent of the course). Recommend texts and
chapters where the learner already knows about 95 % of the words. Builds on the reader's coverage rule (#68:
`docs/contracts/reader/README.md` "Coverage", `apps/web/src/lib/features/reader/coverage.ts`): token = a match with a
word character, type = the first candidate's entry id, coverage = `floor(100 × known tokens / tokens)`, a
book's coverage sums the token counts of its chapters. Contract: `docs/contracts/reader/read-next.json` and the
route shape (expected contract 18). Builder: one agent, branch `feature/v090-read-next` from `develop`.
Test first in every task; one commit per task.

## Shape

- **Where the work happens.** The *known* set lives on the client (marks, reviews, declarations), the text lives
  on the server. So the server caches, per chapter, the **type counts** (`{entryId: tokens}` plus the token total
  and the unmatched count), and the client intersects them with its known index. Nothing about the learner's
  known words goes to the server (privacy: "computed locally"). Coverage for a book is recomputed from cached type
  counts only when the known set changes (a version stamp of the known index), never per page view.
- **Server cache:** table `chapter_types` keyed by `(language, content_hash)` (a hash of the chapter text and the
  segmenter/dictionary versions) holding the counts as compact JSON; filled lazily by `GET
  /api/library/books/{id}/types?chapter=<n>` and `GET /api/library/books/{id}/types` (all chapters, paged), invalidated
  by a dictionary or segmenter change (the version is part of the key). Cost bound: segmenting runs once per
  chapter per version; a request that would segment more than N chapters (default 20) answers the cached part and
  queues the rest (the page shows "analysing 14 of 60 chapters").
- **Candidates (Ruling 1):** the learner's library (books and chapters), the graded reading library (#231) and
  the texts of the course (#223), all text **already on the server**. Texts imported by the learner (#69) join
  automatically when that issue exists. Not in v0.9.0: Aozora/Gutenberg catalogue items that are not downloaded
  (overview decision 12).
- **Score** per candidate (a chapter or a graded text): `cov` (the coverage fraction above), `unknownTypes`
  (distinct unknown types) and `tokens` (length). Eligible when `cov` is within the learner's target band
  (default 0.95, adjustable 0.90–0.98, band ± 0.03) and `unknownTypes ≤ 60`. Rank by `|cov − target|`, then fewer
  unknown types, then shorter. A book's suggestion is its **next unread chapter** (the library position).
- **UI:** "Read next" on the reader library page (three suggestions, each "94 % known · 23 new words · 12 min" and
  one line of reasoning: "Close to your 95 % target"), an optional Home widget (off by default, switch in
  Settings → Reader), a target control (a slider with the reasoning line) in the reader settings.

## Tasks

1. **Rule and fixtures first** (`docs/contracts/reader/read-next.json`): candidates with type counts and a
   known set → coverage, unknown count, eligibility and ranking, ties, the next-unread-chapter rule, a target at
   both ends of the range, an empty library. Reviewed before code.
2. **Pure scoring** `apps/web/src/lib/features/reader/readNext.ts` + contract test; reuse `coverage.ts` for the
   token rule (no second definition of "known").
3. **Server cache:** migration (`chapter_types`), `library` package function `ChapterTypes`, routes, the
   version key; tests: a second request does not segment (counter), a changed dictionary version recomputes,
   a foreign user's book is 404, the paged all-chapters form, the queue bound.
4. **Known-index stamp** on the client (a cheap hash of mark rows and the card list, or the sync cursor) so the
   score is recomputed only when the stamp changes; test: no recompute on a page revisit.
5. **Loader** (`readNextLoad.ts`): fetch the type counts for the candidates, with an in-memory plus IndexedDB cache
   keyed by `(content_hash, stamp)`; offline: scores what is cached.
6. **UI:** the library section, the Home widget (via the widgets API) and the settings control; jsdom tests; empty
   states ("Add a book or open the graded readers"), loading ("analysing…"), nothing eligible ("Everything
   is a bit hard or easy: widen your target").
7. **Docs:** wiki `Reader` (Read next), contracts README + CHANGELOG (expected 18), ROADMAP.
8. **Verify:** Go `library` tests with `-race`, `npm run check`, `npm test`, merge `origin/develop`, PR.

## Rulings

- Ruling 1: **only text already on the server** is a candidate — scoring a catalogue text needs a fetch and a
  licence line per text — if wrong, "read next" misses Aozora/Gutenberg suggestions (cost: a later source
  adapter; the scoring is source-agnostic).
- Ruling 2: **the server caches type counts, the client scores** — the known words are client state and stay
  private, and the cache is shared by every learner of a server — if wrong, a very large library makes the type
  route heavy (cost: the queue bound and the paged form; counts are about 5–10 KB per chapter).
- Ruling 3: the default target is 95 % with a ±3 % band, adjustable 90–98 — the issue's figure — if wrong,
  suggestions are too hard or too easy (cost: the slider).
- Ruling 4: coverage counts **tokens** (as the reader does), the difficulty hint counts **distinct unknown
  types** — repeated unknown words in one story are cheap, many different ones are not — if wrong, ranking
  disagrees with a learner's feeling (cost: a constant).
