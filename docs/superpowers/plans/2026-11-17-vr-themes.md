**Goal:** Themes become data. A new pack type `theme` (a `themes.json` holding one or more colour themes)
installs through the existing staged upload, whose licence review now also shows the **measured contrast** of
every theme; the built-in themes (the eight approved ones plus every candidate whose licence checks out) ship
inside the binary and are always present;
`GET /api/themes` lists every theme with its colours and credits; the derived tokens (hair, on-accent, accent
tints, mastery ramp, reader word marks, highlight and selection washes, correction marks, the reading accent and
the accent picker list) are one documented algorithm with fixtures run by Go and the web; the person's choice is
the user-global row `qinqin-core` / `appearance` (syncs, backs up). The web applies the tokens on `:root`, keeps
the last applied tokens for first paint, and gets Settings → Appearance with a live preview and a quick theme
switch.

**Design (binding):** `docs/superpowers/specs/2026-11-16-visual-rework-design.md` §6 (tokens), §7 (themes, theme
packs, appearance row), §12 (Android); mockups `docs/superpowers/specs/assets/2026-11-16-visual-rework-mockups.html`
(`THEMES` object: the palette values of the eight approved themes). Direction:
`docs/superpowers/directions/2026-11-17-visual-rework.md`.

## Global constraints

- Licensing first. A palette is bundled only after its upstream LICENSE file was fetched and read; the copy is
  committed verbatim as `server/internal/themes/builtin/<pack>/LICENSE` and travels in the binary (MIT asks for the
  notice with every copy). Each built-in pack is credited in `docs/sources.md` and by `GET /api/themes` (the
  Sources page reads it). A palette whose licence is unclear is not bundled (Ruling in the Execution record).
- Colour values: the eight approved themes take the mockup's `THEMES` values, cross-checked against the upstream
  palette files; a mockup value that is not the upstream value of the role the mockup meant is corrected to the
  upstream value (Ruling). The mockup's `board` (the mockup page background) is not a theme token.
- Theme files are strict: unknown members, repeated members, upper-case hex, `#rgb`, alpha are refused. All error
  codes and paths are pinned by `theme-file.json`.
- Contrast is measured and reported (staged review, contract), never a reason to refuse a pack (design §7).
  Built-in themes must reach 4.5:1 for `text` on `panel` (a Go test); every other measured pair of the built-ins is
  recorded in the Execution record.
- Derived tokens are never stored in a theme file; one algorithm (`themes/README.md` "Derived tokens"), the same
  numbers in Go and TypeScript (`derive.json`).
- `appearance` is a plain `qinqin-core` plugin data row: no server validation, no typed table, no migration of its
  own. Missing row = the defaults. Unknown keys kept on write.
- No literal colours in components (tokens only), no third-party host at runtime, no CSS framework. All new
  strings in `apps/web/src/lib/i18n/messages/en.json` (`settings.appearance.*`, `packs.contrast.*`,
  `sources.themes.*`, `account.menu.theme*`), via `t()` / `<Msg>`.
- Accessibility survives: skip link, focus, live regions, reduced motion, forced colours (the reader's word states
  keep their forced-colours path), screen-reader names. Theme choice never removes a text or shape cue.

Rules pinned here:
- `themes.json` is a JSON array of 1..64 theme objects, at most 256 KiB. A theme has exactly the members
  `id` (`^[a-z0-9]+(-[a-z0-9]+)*$`, ≤ 64 bytes), `name` (1..64 code points, no control characters, no leading or
  trailing space), `family` (optional, same rule as `name`), `scheme` (`light` | `dark`), `colors` (exactly the
  13 keys `chrome panel raised line text muted good warn bad gradeAgain gradeHard gradeGood gradeEasy`, each
  `^#[0-9a-f]{6}$`), `accents` (1..16 members, key `^[a-z][a-z0-9-]{0,31}$`, value a colour; **file order is
  kept**), `defaultAccent` (a key of `accents`). Ids unique within the file. A repeated member in any object is
  refused.
- First error wins, checked in this order: size, JSON, top-level array, count; then theme by theme: object,
  repeated member, unknown member (first in file order), missing member (in the order above), `id`, duplicate id,
  `name`, `family`, `scheme`, `colors` (object, repeated, unknown, missing / bad value in the token order),
  `accents` (object, repeated, count, each key then value in file order), `defaultAccent`.
- Error codes: `too-large`, `bad-json`, `not-an-array`, `no-themes`, `too-many-themes`, `not-an-object`,
  `duplicate-member`, `unknown-member`, `missing-member`, `bad-id`, `duplicate-id`, `bad-name`, `bad-family`,
  `bad-scheme`, `bad-colour`, `no-accents`, `too-many-accents`, `bad-accent-key`, `bad-default-accent`; path in
  the form `$[1].colors.panel`.
- Contrast: WCAG 2.2 relative luminance (sRGB channel `c/255`, `c <= 0.04045 ? c/12.92 : ((c+0.055)/1.055)^2.4`,
  weights 0.2126 / 0.7152 / 0.0722), ratio `(L1+0.05)/(L2+0.05)` with L1 the lighter, **rounded to two decimals
  (half up)**; a check passes when the rounded ratio is ≥ its minimum. Review checks in this order: `text`/`panel`,
  `text`/`chrome`, `muted`/`panel`, `muted`/`chrome` (4.5); `gradeAgain`, `gradeHard`, `gradeGood`, `gradeEasy`
  on `panel` (3); every accent `accent:<key>` on `panel` (3) in file order.

- `accentKey` = the requested key when it is in `accentChoices`, else `defaultAccent`. `accent` = its colour.

- `hair` = `alpha(line, 55)`; `accentTints` = `{14, 32, 58, 100}` of `accent`; `primaryWash` = `selectedWash` =

  `correctionMarks` = `{mistake: {color: gradeAgain, style: "wavy"}, suggestion: {color: gradeEasy, style:
