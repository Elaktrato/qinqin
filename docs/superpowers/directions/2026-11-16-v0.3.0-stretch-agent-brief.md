## Process per item

- Spec (≈150–250 lines, YAGNI, answered by you in brainstorming style) → plan (small test-first
  tasks, exact files, interfaces, gates, review focus, real-app check steps) → implementation,
  subagent-driven: one implementer subagent per plan (or per few tasks), strictly test-first (see the
  test fail, then pass), one commit per task.
- Then an independent REVIEW by a separate read-only subagent on the strongest available model
  (security focus for anything with auth, tokens, files, mail). Treat its must-fix findings as
  blocking; send ONE fix wave to the builder; mutation-check at least three of the new tests (break
  the code, see a test fail).
- Merge topic branches `--no-ff` into your collection branch. When an item is complete and all
  gates are green, merge the collection branch into `develop` (`--no-ff`), push `develop`, and
  WAIT for CI on that commit to be green. If CI is red, fix it before anything else. Then comment on
  and close the issue, update `docs/ROADMAP.md` and the README where behaviour changed.
- Never let `develop` stay red, and never push unreviewed work to it.

## Hard rules

- Never touch `main`; never tag or release; never rewrite published history or force-push; never
  delete branches you did not create. Topic branches: `feature/v030s-<name>` or `docs/v030s-<name>`,
  one git worktree each (`git worktree add -b <branch> .claude/worktrees/<dir> <base>`).
- Commit messages are conventional (`feat(scope): …`), each ending with a blank line and exactly
  `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>` (the owner's instruction for this project).
- Secrets, passwords, tokens, one-time codes never go into logs, API responses, fixtures or commits.
  Authorization tests on every new route (every route is a `route{}` row in `routes()` with the
  right access value; the route-walk and the PWA route fixture tests will fail until both are
  updated: regenerate the fixture with `UPDATE_ROUTES_FIXTURE=1` and decide whether the new route
  may be cached; the default is no). Enumeration-safe responses on auth endpoints, constant-time
  comparisons, user isolation tests (two users).
- Unclear-licence data is fetched locally, gitignored, never bundled. Licensing first, then best UX
  even at higher development cost.
- No browser automation (Playwright, Chromium, puppeteer) on this machine. Test UI with vitest
  (jsdom component tests `*.dom.test.ts`, unit tests) and drive a built server with curl or Python.
- Go is not installed. Run Go in Docker as your own user with a shared cache and a shared lock so
  gates never run concurrently:
  `flock /tmp/qinqin-go.lock docker run --rm -u $(id -u):$(id -g) -e HOME=/tmp -e GOPATH=/gp -e GOCACHE=/gc -v <cache>/gp:/gp -v <cache>/gc:/gc -v <worktree>:/src -w /src/server -e GOTOOLCHAIN=auto -e GOFLAGS=-buildvcs=false golang:1.26 sh -c "gofmt -l . ; go vet ./... && go test -count=1 -p 2 -timeout 30m ./..."`
  (targeted packages per task; ONE full run before the last commit of a branch; `-race` only on
  packages whose concurrency you changed, never on the whole api package). Afterwards `git status`
  must be clean and `find <worktree> -user root -not -path '*/node_modules/*'` empty (remove
  root-owned files via a container).
- Web gates: `npm --prefix apps/web ci`, then `run check`, `test`, `run build`, and READ the exit
  codes (do not hide them behind `| tail`). `npm run check` must pass: CI runs it. CI uses Node 26:
  run the full vitest once in the `node:26` Docker image before merging.
- The machine has 4 cores shared with other work: at most 2–3 parallel subagents.
- Real-app checks: build the server from a scratch copy, run it on a free 127.0.0.1 port (never
  8080, 8085, 8300), drive it with curl/Python, then kill and delete everything you started. NEVER
  touch the container named `qinqin` (127.0.0.1:8085), `/home/user/qinqin-deploy`, or any other
  project's containers.
- Component logic goes into tested pure modules; Svelte components stay thin. README and
  `docs/wiki/` are updated where behaviour changes.
- Report honestly in specs, plans (Execution record) and the handoff: say what was not verified.
