# Installable PWA with offline study — design (#79, v0.3.0 item 6)

Status: Draft (2026-11-15), written unattended; **Ruling: what — why — cost if wrong** marks every
non-obvious call. Nothing is built. Direction item 6; issue #79 ("a stopgap: Android remains the
planned native client"). Builds on: the review outbox (`apps/web/src/lib/study/events.ts`), the event
and sync routes (`POST /api/events/batch`, idempotent ULIDs), static serving rules (#20,
`server/internal/webdist`), the learner's day (`GET /api/me/time-zone`), daily limits and vacation
(item 4/4b: queue shaping from plugin rows), accounts (`POST /api/auth/logout`, sessions).

## What exists (checked on `feature/v0.3.0` b925e17)

- SPA via `adapter-static` (`build/`, fallback `index.html`), embedded in the Go binary. `index.html`
  is `no-store`, `_app/immutable/*` is immutable for a year, other files get no `Cache-Control`.
- No manifest, no icons, no favicon, no service worker, no Cache API use. Fonts are system stacks.
- Bearer token in `localStorage['qinqin.token']`, sent as `Authorization` by `lib/api/client.ts`.
- Review outbox: `localStorage['qinqin.study.pending']`, flushed on boot and on `online`, one event at a
  time, permanent 4xx dropped. It is **not tied to a user**: a different user signing in on the same
  browser flushes the first user's reviews into 404s (dropped). Signed out it keeps the queue.
- The study session loads `GET /api/sync/pull?cursor=1970-01-01T00:00:00Z&collections=pluginData,pluginStates`
  (`SYNC_PULL_PATH` in `lib/study/store.ts`: every plugin row of the user, all workspaces),
  `GET /api/events?since=1970-01-01T00:00:00Z&workspace=W` (the whole log, `fullLogPath` in
  `lib/events.ts`) and `GET /api/entries/{id}` per shown card; reverse/cloze
  companions create cards with `PUT …/data/card:<id>` on their first grade.
- Queued reviews are **not merged** into the loaded history: a reload before the flush shows reviewed
  cards as due again (also online). Fixed here.

## Goals / non-goals

Goals: installable (manifest, icons, standalone); app shell opens offline; the active workspace's
study queue for today works offline; reviews queue and sync on reconnect; nothing of one user is
served to another; a clear update flow; clear offline states. Non-goals: offline reader, journal,
search, dictionary browsing, offline card creation/editing, push notifications, Background Sync.

## 1. Manifest and icons

`static/manifest.webmanifest`: `name` "qinqin 勤勤", `short_name` "qinqin", `id` "/", `start_url`
"/", `scope` "/", `display` "standalone", `theme_color` "#0b6bcb", `background_color` "#ffffff",
icons 192, 512 (`purpose: any`) and 512 maskable; `app.html` gains `<link rel="manifest">`,
`<link rel="icon" href="/favicon.svg">`, `apple-touch-icon` (180 px PNG), `theme-color` meta.

Ruling: an own-made geometric mark, drawn by a committed script — no existing brand art exists, the
勤 glyph would come from a font (licence and rendering vary), and own art is licence-clean — cost if
wrong: a designer replaces five files. The mark: brand-blue rounded square; two white rounded
"seal" squares side by side (the doubled 勤勤), each crossed by one blue horizontal and one vertical
stroke. `apps/web/scripts/icons/raster.mjs` rasterises rounded rectangles with 4×4 supersampling and
writes PNG with `node:zlib` (no dependency); `make-icons.mjs` writes `static/icons/*.png` and
`static/favicon.svg` from the same shape list. Outputs are committed; a test regenerates and compares
bytes.

## 2. Service worker: shape and policy

SvelteKit's `src/service-worker.ts` (uses `$service-worker`: `build`, `files`, `version`), with all
decisions in pure modules under `src/lib/pwa/sw/` taking injected `caches`, `fetch`, `crypto` (tested
in vitest with fakes). `kit.serviceWorker.register = false`; `lib/pwa/register.ts` registers only in a
secure context (`window.isSecureContext`), so plain-HTTP LAN installs behave exactly as today.
`kit.version.name` = `process.env.QINQIN_BUILD_ID ?? git short hash ?? Date.now()`.

Ruling: hand-written on SvelteKit's service worker instead of Workbox (MIT) — the user partitioning,
auth handling and allowlist are custom anyway and Workbox adds a build plugin and ~20 KB for
strategies we can write in 150 tested lines — cost if wrong: we re-implement a caching edge case
Workbox already handles.

**Request classes** (`classify(request) → kind`, table-tested):

| Kind | Matches | Strategy |
|---|---|---|
| `shell` | `build` files, `/`, `/manifest.webmanifest`, `/icons/*`, `/favicon.svg` | precached per version, cache-first |
| `navigate` | `mode === 'navigate'` same origin, not `/api/` | network-first (4 s) → cached `/` |
| `hanzi` | `GET /hanzi/U*.json` | cache-first, runtime, cap 4 000 entries |
| `api` | allowlisted `GET`s (below) with an `Authorization` header | network-first (8 s) → partition cache |
| `bypass` | everything else (all non-GET, other origins, `/api/auth/*` except `me`, `/api/account/*`, `/api/admin/*`, exports/tickets, AI, journal photos, audio clips, lookups) | not touched |

API allowlist (exact paths, query normalised by sorting keys): `/api/auth/me`, `/api/workspaces`,
`/api/plugins`, `/api/languages`, `/api/me/time-zone`, `/api/sync/pull` **only** when `collections`
is set and a subset of `pluginData,pluginStates` (a pull without it is the whole dictionary delta),
`/api/plugins/{id}/data` and `/data/{key}`, `/api/events` (with `workspace=`), `/api/entries/{id}`.
Only `200` responses are stored. Fallback to the cache happens on a network error, the timeout, or
502/503/504; any other status passes through (a 401 or 404 is the truth, not a reason for old data).
A response served from the cache is re-wrapped with headers `X-Qinqin-Offline: 1` and
`X-Qinqin-Saved-At: <ISO>`; `lib/api/client.ts` reports them to the offline store (§5).

Ruling: an allowlist, never "cache all GETs" — a new route must opt in, so admin data, lookups and
anything secret are never stored by accident — cost if wrong: a page that should work offline needs a
one-line allowlist change.

## 3. Never another user's data

- **Partition by credential:** the `api` cache name is `qinqin-api-v1-<hex(sha256(Authorization))[:32]>`.
  The worker never reads `localStorage` (it cannot); every request carries its own token, so a request
  can only ever be answered from the cache filled with the same token. A different user — or the same
  user after a new login — has another token and therefore another, empty partition.
- **Cleanup:** on sign-in and on boot with a token, the page deletes every `qinqin-api-v1-*` cache except
  its own (`lib/pwa/partitions.ts`, page-side `caches`); on logout it deletes all of them. The worker
  deletes the partition of a request answered 401.
- **Requests without `Authorization`** are never cached or answered from a partition.
- **After a personal restore** (backup spec §4) the device that restored deletes its partitions,
  clears the workspace selection and the queued reviews of the old workspace ids, and reloads; other
  devices were signed out by the restore and start over with new tokens and partitions.
- **Outbox per user** (`events.ts`): the queue becomes `qinqin.study.pending.v2` =
  `[{userId, event}]`; the legacy key is adopted by the first signed-in user (today's behaviour) and
  removed. Flush sends only the current user's items. Explicit logout first tries one flush; if items
  remain, a dialog says "N reviews have not been sent yet. If you sign out now they are deleted from
  this device." with **Stay signed in** (default focus) and **Sign out and delete them**. Items of
  another user (left by an expired session, never by a logout) are kept 30 days, never flushed or shown
  for anyone else.

Ruling: partition by a hash of the bearer token, not by user id — the worker learns no identity, a
logout or revoke makes old caches unreachable even if cleanup fails, and nothing can map one user's
request to another's cache — cost if wrong: a re-login starts with an empty offline cache (refilled on
the next online visit).
Ruling: logout with unsent reviews asks instead of silently keeping or dropping them — keeping them
would leave a user's data behind a logout, dropping them is silent loss — cost if wrong: one dialog.

## 4. Offline study

- **Preparation** (`lib/pwa/prepareOffline.ts`): when a worker controls the page and the device is
  online, after Home or the study page has loaded the active workspace's study history, it computes the
  queue a session would start with now (`buildQueue`/limits/vacation/burying of items 3 and 4b, through
  the existing pure functions and the saved session config) plus the next 50 new cards, and fetches
  `GET /api/entries/{id}` for those entries (≤ 500, concurrency 2) and `/hanzi/U*.json` for the
  characters of writing cards — normal `fetch`, so the worker stores them. The request URLs are built
  by the same exported helpers the pages use. Throttled per workspace: once per 30 min or when the card
  count or event count changed. Never on `navigator.connection.saveData`.
- **History merge**: `loadStudyDataWith` (`lib/study/store.ts`, under `loadStudyData` and the cached
  `loadStudyHistory`) merges the current user's queued reviews of that workspace into the log before
  `canonicalCards` (dedupe by id) — online and offline — so a reviewed card never reappears as due before the flush.
- **What is studied offline**: real cards only. `planCompanions` gets `offline: true` (from
  `navigator.onLine === false` or the last API response being an offline one) and plans no virtual
  reverse/cloze/sentence/writing/tone items, because creating a card is a plugin-data write.
  Grading records reviews into the outbox exactly as today.
  Ruling: no offline card writes — the outbox is events-only and plugin data is LWW keyed rows that a
  second offline queue would have to replay in order — cost if wrong: fewer items in an offline session
  (the session start says "Companion cards return when you are online").
- **Sync**: unchanged rules (one event at a time, same ULID, permanent 4xx dropped). Triggers: boot,
  `online`, `visibilitychange` to visible, and every 60 s while items are queued and the page is
  visible. Ruling: no Background Sync API — Safari and Firefox lack it and a worker cannot read the
  `localStorage` outbox — cost if wrong: reviews sync when the app is next opened, not in the background.
- **Day and limits offline**: the time-zone response is cached; the day, vacation and limits are
  computed from cached rows exactly as online.

## 5. Offline UX

`lib/pwa/offlineState.ts` (store: `online`, `servedFromCacheAt`, `queued`, `prepared:{workspaceId,
cards, at}`) and `OfflineBanner.svelte` in the root layout (`role="status"`, never colour alone):

- offline, nothing queued: "You're offline. Study works with saved cards."
- offline with queue: "You're offline. 3 reviews are saved on this device and will be sent when you're
  back online."
- data from cache while online-ish (server unreachable): "Can't reach the server. Showing saved data
  from 14:02."
- back online and flushed: "All reviews sent." (5 s).
- study page offline without a prepared queue: "This workspace isn't ready for offline study yet. Open
  it once while online." Pages that need the network (reader, search, journal, settings) keep their
  existing error states plus the banner.
- **Settings → Account → App** (every user): Install button (`beforeinstallprompt`, Chromium), iOS text
  ("Share → Add to Home Screen"), "Offline: ready — 120 cards saved at 14:02", storage use
  (`navigator.storage.estimate()`), "Clear offline data", and the HTTPS note when not a secure context.
  `navigator.storage.persist()` is requested once when running standalone.

## 6. Updates

- New build → new `service-worker.js` bytes (`version`) → the browser installs it in the background
  (checked on navigation and by `registration.update()` hourly while open). `install` precaches the new
  shell into `qinqin-shell-<version>`; it then **waits**.
- The page sees `registration.waiting` → banner "A new version of qinqin is available. [Reload]".
  Reload posts `{type:'skip-waiting'}`; on `controllerchange` the page reloads once (guarded).
  `activate` deletes other `qinqin-shell-*` caches and old `qinqin-api-v<n>` generations, then
  `clients.claim()`.
- The very first install claims clients immediately (nothing to be inconsistent with).

Ruling: never `skipWaiting` on its own — a silent swap mid-session can load new code against an old
page — cost if wrong: users run an old build until they press Reload or close every tab.

## 7. Server and deployment

- `webdist`: `service-worker.js` → `Cache-Control: no-cache`; `manifest.webmanifest` →
  `application/manifest+json`, `no-cache`; `/icons/*`, `favicon.svg` → `public, max-age=86400`.
  `index.html` stays `no-store`, immutable assets unchanged (#20).
- README "Reverse proxy and HTTPS" + deploy notes: install and offline need HTTPS (or
  `http://localhost`); the proxy must pass `Authorization` and must not cache `/service-worker.js`;
  over plain HTTP the app works without install/offline. iOS may evict offline data after weeks
  unused; reviews queued on a device are only safe once sent.
