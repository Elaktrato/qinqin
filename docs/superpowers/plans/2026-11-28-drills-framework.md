# The drills framework and the Practice area (2026-11-28)

Milestone v0.9.0, phase 5 (plan §3 "Drills framework", §5). No GitHub issue of its own; it is built once, before the
four drills that use it: the conjugation trainer (#178), measure words and counters (#179), tone pairs (#180) and
look-alike characters (#228). Branch `feature/v090-drills-framework` from `feature/v0.9.0` (87de30a5).

## What (owner decisions)

- **Items:** each drill item (word × form family, a noun, a tone pair, a look-alike set) has its own spaced schedule:
  FSRS, derived from events the way flashcards are, outside the flashcard queue.
- **Events:** each drill has its own event type.
- **Practice area:** one Practice area lists the drills and has a "Practise weakest" round across them.
- **Shared study core:** it uses `lib/studycore` and `lib/exercises` (#278) and never imports flashcards.
- **Counting:** drill work counts in stats, EXP and goals, mirroring the grammar events (#277).
- **Contract first:** `docs/contracts/drills/` with a README and fixtures decoded by Go and web: item keys, the
  event shape, schedule derivation, the weakest-round pick, counting. ContractVersion 24 (23 on the base).
- **Phone first:** 360 px, no sideways scroll, `/practice` in `phone-width.spec.ts`; hidden romanisation respected;
  works in the Android WebView shell.

## The design

### Drills, items, events

- A **drill** has an id (`^[a-z][a-z0-9]*(-[a-z0-9]+)*$`, at most 32 characters, never `weakest`). Its event type
  is `drill.<id>`. The registry of drills a server and a client count is the contract's `registry` list (Go
  `drills.IDs`, web `DRILL_IDS`); it starts **empty**: each drill's builder adds its id there, in `stats` and in the
  web's drill list (README "Adding a drill").
- An **item key** names one scheduled item inside a drill: 1 to 200 code points, no white space (Unicode
  `White_Space`) and no control characters (`Cc`). Its structure belongs to the drill; the README lists the planned
  shapes (`<entryId>:<formFamily>`, `<entryId>`, `<t1>-<t2>`, the set's characters).
- **Event:** `{type: "drill.<id>", payload: {item, mode, grade}}` (member order part of the shape; a drill may add
  members after these, a client ignores members it does not know). `mode` is the drill's direction (same pattern
  as the id), `grade` 1 Again, 2 Hard, 3 Good, 4 Easy, as a review.
- **Parse:** a client reads an event as a drill answer when the type is `drill.` + a valid id, the payload is an
  object with a valid item, a valid mode and an integer grade 1..4, and `ts` parses. Anything else counts nowhere.

### Schedule

Per (drill, item) of a workspace: the answers in `(instant, id)` order replayed through ts-fsrs exactly as a card's
reviews are (`studycore/scheduler.ts`: an empty card at the first answer, `next(card, t, grade)`, the study clock with
vacation days frozen), with the **default FSRS weights** (not the workspace's flashcard parameter set). Retrievability
at `now`: `forgetting_curve(w, elapsedDays, stability)` with `elapsedDays = max(0, v(now) − lastFed) / DAY`.

### Picks

- **A drill's round** (`round`): from the drill's candidate items (in the order the drill introduces them): the due
  items (`due <= now`), earliest due first; then new items (no answer yet), in the drill's order, at most
  `newPerRound` (10); then items not due yet, lowest retrievability first; at most `roundSize` (20). Answered items
  that are no longer candidates are not picked.
- **Practise weakest** (`weakest`): across the drills that apply to the workspace, every candidate item with at least
  one answer, lowest retrievability at `now` first, then drill id, then item key; at most `roundSize`.

### Counting

- **Activity** (heatmap, weekly summary, goals): one `count` rule per registered drill, type `drill.<id>`, feature
  `practice`: every answer is a point; a daily goal `activity:drill.<id>` counts answers.
- **EXP:** 5 per drill answer plus the review grade bonus (0, 0, 5, 10); the daily bonus stays a review bonus.
- **Streak:** a learner day with a drill answer counts, everywhere the streak is shown, and for the milestones'
  `streak` and `days-active` families.

## Rulings

- Ruling: **Practice is a core feature** `practice` (a per-user switch in Settings → Features, on by default, like
  Stats since #295), placed after Scripts and before Stats — the plan calls it an "area" next to Decks, Reader and
  Grammar, the four drills are study activities a learner may not want, and the switch mechanism exists (#294 made
  new ids free of migrations) — cost if wrong: one id more in `features.IDs` and `switches.json`.
- Ruling: Practice shows in the navigation only while **a drill applies to the workspace language** (`appliesTo` is
  "some registered drill applies"); `/practice` itself always answers, with "No drills for this language yet" when
  none applies — no empty section in the bar before the first drill ships, and a direct link still works — cost if
  wrong: none for users; until #178–#228 land, Practice is not in the bar.
- Ruling: the **registry starts empty**; the framework registers none of the four drills — their ids, event types and
  activity words belong to their builders, and a registered drill shows up as a goal choice and an activity row, which
  must not happen before the drill exists — cost if wrong: each drill builder adds one id in three places (the README
  checklist, and a test that the three lists agree).
- Ruling: **the reference drill** is a sample drill (`sample`, items `sample-1`…`sample-5`, a "Right"/"Wrong" pair of
  buttons) in `lib/features/practice/sample/` (not `testing/`: it ships in the bundle), registered only when the device has the developer flag
  `localStorage["qinqin.dev.drills"] = "sample"` (set by DOM tests and e2e, never by the app). It proves the whole path
  in a real browser at 360 px: list, round, outbox, server, the weakest round. It is not in the registry, so the
  server counts none of its events; the web's EXP and streak count every parsed drill answer (see below), so a sample
  answer earns EXP on a test account — cost if wrong: a few hundred bytes of test code in the bundle; a developer who
  sets the flag on a real account gets sample events in their log (harmless, never in activity).
- Ruling: a client **parses every `drill.<valid id>` event** (not only registered ids), and EXP and the streak count
  every parsed answer; the server's **activity** counts registered drills only — a newer client's drill keeps the
  streak on an older one, and activity needs a per-type rule in Go anyway — cost if wrong: a learner using a drill the
  server does not know yet sees it in EXP and the streak but not on the heatmap until the server is updated.
- Ruling: event type `drill.<id>` (one type per drill, the owner's "own event type") with a common payload
  `{item, mode, grade}` — the activity rule counts per type, so each drill is its own activity row and goal; one
  payload shape lets the core schedule, pick and count every drill — cost if wrong: a converter (events are immutable).
- Ruling: a drill answer carries an **FSRS grade** (1–4), not right/wrong — FSRS needs a grade, and a drill can say
  Hard for a right answer after a hint (#180 tone pad, #178 IME) — cost: none; a drill that only knows right/wrong
  writes 3 or 1.
- Ruling: the **schedule key is the item**, whatever the mode — #178's "word × form" is one item whether the form is
  produced or recognised; a drill that wants separate schedules puts the direction into its item key — cost if wrong:
  both directions share one memory estimate.
- Ruling: drills use the **default FSRS weights**, not the workspace's flashcard parameter set — those weights are
  optimised on flashcard reviews, a different task; the default is the honest start, and one constant keeps the
  contract simple — cost if wrong: drill intervals are not personalised (a later issue may add a drill parameter set).
- Ruling: the **study clock** (vacation) applies to drills as to cards — vacation days are neutral everywhere else —
  cost: none.
- Ruling: "weakest" is **lowest retrievability now** over the items with at least one answer, no per-drill cap —
  retrievability is FSRS's own measure of how likely an answer is right now; unseen items have no measure — cost if
  wrong: a round may come from one drill only when that drill is the weakest.
- Ruling: a drill's round is due → new (at most 10) → not yet due (lowest retrievability), 20 items; no re-ask of a
  wrong item inside a round — practice is voluntary, so a round is never empty while there are items, and the next
  round picks a wrong item as due (FSRS's 1-minute learning step) — cost if wrong: a learner who wants an item again
  at once starts another round.
- Ruling: **activity** is a `count` rule per drill (every answer a point), as the scripts trainer — a drill answer is
  one question answered, like a script answer — cost if wrong: a long round gives many points on one day.
- Ruling: **EXP** is 5 per answer plus the review grade bonus (0/0/5/10), no daily bonus — a drill question is
  smaller than a flashcard (tone cards give 8 base); the daily bonus is defined on reviews, as for grammar — cost if
  wrong: drill-only days give less EXP than review days.
- Ruling: `StudyHistory.drillAnswers` is **optional** (`historyOf` always sets it, absent means none) — unlike
  `grammarRuns`, so the 22 test mocks of the history stay untouched while two other builders work on the same
  branch — cost if wrong: a new reader of the history could forget the drill answers; the callers that count EXP and
  the streak are tested.
- Ruling: the Go side decodes the keys, payload and activity parts; **schedule and pick are web-only** — the server
  has no FSRS (flashcard schedules are client-derived too); the fixtures are generated from plain ts-fsrs by an
  oracle that shares no code with the web module — cost if wrong: an Android client reimplementing them reads the same
  fixtures.
- Ruling: rounds are **routes** (`/practice/<drill>`, `/practice/weakest`) — the Android back button and the
  browser's back leave a round, a reload restarts it — cost: a reload loses the round's place (the answers are
  already saved).
- Ruling: a drill's question component gets each new item **without being remounted** (no `{#key}`), so a typed
  answer field can keep focus and the phone keyboard stays up between questions — the brief's "no keyboard
  dismissal" in the WebView — cost: a drill component resets its own state when `item` changes.
- Ruling: the framework never shows a reading; an item's label is the drill's (`label(item)`), and a drill that shows
  a reading uses `useRomanisation()`/`ReadingText` as every screen does (the romanisation lint covers its
  components) — cost: none.
- Ruling: icon `repeat` (already vendored) for Practice — no new icon vendoring — cost: none.
- Ruling: a new i18n key area `practice` — the drills' strings get a home of their own — cost: none.
- Ruling (made while building): `DRILL_ANSWER_XP` lives in `studycore/exp.ts` and `drills.ts` re-exports it — `drills.ts`
  imports the scheduler, which re-exports from `exp.ts`; a value import the other way would be a cycle — cost: none.
- Ruling (made while building): a phone bar title for `/practice/...` without a Practice section (no drill applies)
  comes from the route titles (`pageFrame.svelte.ts`, first path segment for `/practice` only), and the page sets its
  own title (`setFrameTitle`) — every route needs a title of its own (`pageFrame.test.ts`) — cost: none.
- Ruling (made while building): every drill answer marks the event log stale (`changesLog` in
  `activity/sources.ts`), registered or not — EXP and the streak read every parsed answer — cost: none.
- Ruling (made while building): the Next button takes the focus after an answer only when the focus was lost (the
  answer buttons went away), never from a field — a typed answer keeps the keyboard up — cost: none.
- Ruling (made while building): a round counts Hard, Good and Easy as right and lists the Again items once each as
  "To practise again" — Hard is a right answer after a hint — cost: none.
- Ruling: ContractVersion 24 (23 on the base; the orchestrator renumbers on merge).
