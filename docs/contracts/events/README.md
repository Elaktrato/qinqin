# Study events: envelope, payloads, review parsing, activity scoring

A study event is one append-only row a client records (a review, a reading flush, a journal save, …) and the
server keeps. Everything the learner sees as progress (schedules, XP, streak, heatmap, goals) is derived from
these rows on the client or the server. This folder pins how a client writes an event, what the server does
with it, and what each type's payload means. Design: `docs/superpowers/specs/2026-11-17-v040p-contract-gaps-design.md`
(Q1–Q4, Q9; issue #109).

Owner code: `server/internal/api/handlers_events.go`, `server/internal/events/events.go`,
`server/internal/sync/sync.go` (push), `server/internal/sync/page_collections.go` (pull v2). Web:
`apps/web/src/lib/events.ts`, `apps/web/src/lib/study/scheduler.ts` (`sortedReviews`).

Fixtures:

- `envelope.json` — batches posted to `POST /api/events/batch`, the answer, and what `GET /api/events` and
  the pull v2 `events` collection return afterwards. Decoded by `server/internal/api/contract_events_test.go`
  (every step and the stored list), `apps/web/src/lib/study/scheduler.test.ts` (the order case) and
  `apps/web/src/lib/sync/pullPage.contract.test.ts` (the pull case). `$ws` is a workspace of the caller,
  `$bobWs` one of another user.
- `payloads.json` — the payload of each written type (`build`), when the web emits `read` and `journal`
  events (`emit`) and how a consumer counts a `read` payload (`consume`). Decoded by
  `apps/web/src/lib/eventPayloads.test.ts` (the builders of `lib/eventPayloads.ts`, member order included),
  `features/reader/readingTimer.test.ts`, `plugins/journal/entryDraft.test.ts`, `stats/readingTime.test.ts`.
  The restore remap of `view` and `read` payloads is pinned in `backup/remap.json`.

  `sortedReviews`) and `study/exp.test.ts` (XP counts exactly the valid ones).
- `activity.json` — heatmap cells of the built-in activity rules over a case's events (zone history, window

## Envelope

```
{ "id": "<ULID>", "workspaceId": <int>, "device": "<string>", "ts": "<RFC 3339>", "type": "<string>", "payload": <any JSON> }
```

- `id`: a ULID (26 Crockford base-32 characters, parsed strictly: the first character is `0`–`7`), generated by
  the client. It is the event's identity: the same id posted again is a **duplicate**, counted, never an error,
  and the stored copy is never replaced (even when the duplicate's content differs).
- `workspaceId`: one of the caller's workspaces (> 0).
- `device`: free text naming the client (`web` for the web app); absent = `""`.
- `ts`: RFC 3339 with a zone (`Z` or an offset). **The server stores it as UTC whole seconds, the fraction
  truncated (never rounded):** `2026-11-17T10:00:00.789+01:00` is stored and returned as `2026-11-17T09:00:00Z`,
  `09:59:59.999Z` as `09:59:59Z`. A stored event's `ts` can therefore differ from the one the client sent.
- `type`: any string. The server never looks at it (see Declared types).
- `payload`: any JSON value; absent = `null`. The server never validates it, stores its JSON text as sent and
  returns it **compacted** (whitespace removed, member order kept).
- `userId`: never needed; a body value is replaced by the caller's id.

## Routes

- `POST /api/events/batch` `{events: [...]}` → `200 {"accepted": n, "duplicates": m}`. Body at most 4 MiB
  (`413` beyond); no per-event or per-payload cap. `{"events": []}` is `200 {0, 0}`.
- `POST /api/sync/push` `events`: the same envelope and the same storage (`events.Append`); its answer and
  errors are pinned in `sync/push-result.json`.
- `GET /api/events[?since=<RFC 3339>][&workspace=<id>]` → the caller's events with `ts >= since`, all
  workspaces or one, ordered by `ts`, then `id`. `since` is cut to its whole second before comparing, so an
  event of that second is included (`since=…09:00:00.500Z` includes `09:00:00Z`). Unpaged: a second client reads
  the log from the pull v2 `events` collection instead (`sync/`), which is paged.
- Pull v2 `events` ships every type **except `lookup`**.
- `DELETE /api/events/lookups?workspace=<id>` → `{"deleted": n}`: the only deletion of events (the lookup
  history's Clear, #72). No other event is ever changed or deleted.

## Errors

The batch route answers **plain text** (not JSON), with a trailing newline. The events are checked in order
before anything is stored; the first failing check answers and **nothing of the batch is stored**:

| Check | Status | Body |
| --- | --- | --- |
| body not JSON, `ts` not RFC 3339 with a zone | 400 | `malformed request body` |
| `events` missing | 400 | `events array required` |
| `id` not a ULID | 400 | `event id must be a ULID` |
| `ts` missing (zero) | 400 | `event ts is required` |
| `workspaceId` missing or ≤ 0 | 400 | `event workspaceId is required` |
| a workspace not the caller's (unknown or another user's) | 404 | `workspace not found` |
| body over 4 MiB | 413 | `request body too large` |

`GET /api/events` answers `400` text for a bad `since` or `workspace` and `404 workspace not found` for a
foreign workspace.

## Order and the `ts` rule

Clients order events by `(ts, id)`: the instant, then the id as a plain string comparison. The server's list
and the web's `sortedReviews` both do. Two events in one second therefore replay in id order on every device.

Ruling: clients must treat the stored `ts` (whole-second UTC) as the event's time and order by `(ts, id)` —
the web replays its local outbox copy (milliseconds) and the server copy (seconds) through the same order and
ULIDs are monotonic in milliseconds, so two reviews in one second still replay in creation order — cost: a
client that orders by its own millisecond `ts` and a tie-break other than the id disagrees for same-second
reviews. Android should send `ts` already truncated to whole seconds (UTC) so its local copy equals the server
copy byte for byte; the server accepts either.

Ruling: the overview's former "keeps `ts` verbatim" is corrected, not the server — changing storage would
alter every stored log and the pull's string comparison — cost: none.

## Payloads and emit rules

| Type | Shape (written) | Emit rule | Consumers must |
| --- | --- | --- | --- |
| `session` | `null` | at most once per workspace per learner day (per device), when that workspace becomes the current one in the app shell (`routes/+layout.svelte`; a `localStorage` receipt `qinqin.session.<ws>.<day>` is written before the POST) | ignore it (nothing derives from it) |
| `view` | `{entryId: int > 0}` | once per entry page visit (current workspace) | ignore it except backup remap |
| `lookup` | (legacy `{query: string}`) | **never** (#72: the history is the `lookups` row) | ignore it; never ship or cache it |
| `read` | `{bookId: int > 0, seconds: int ≥ 30}` | one event per flush of the reading timer when it holds ≥ 30 whole seconds (time accrues between activity pings while visible; a gap over 120 s counts 120 s; flushed every 5 minutes of accrued time, on page hide, `pagehide` and leaving the book; under 30 s is kept for the next flush of the same book and workspace and dropped on a book or workspace switch), in the **book's** workspace | count `readSeconds(payload)`: 0 unless `seconds` is a finite number ≥ 30, else `min(seconds, 7200)`; points `min(ceil(seconds/300), 24)`; `bookId` may be **absent** (restore of an unknown book) — the time still counts, book unknown |
| `journal` | `{entryId: string}` (the journal entry's ULID) | when a save changed the text, at most once per entry per learner day | count distinct `entryId` **strings** per learner day; a non-string `entryId` never counts |

Member order is part of the shape (`{bookId, seconds}`, not `{seconds, bookId}`): the server stores the JSON text
as sent, so two clients writing the same event write the same bytes. The reading timer
(`features/reader/readingTimer.ts`: `MIN_BURST_SECONDS` 30, `IDLE_CUTOFF_MS` 120 000) is pinned by the `emit`
cases; the 5-minute flush and the 1-second activity throttle are constants of
`features/reader/BookView.svelte` (`FLUSH_EVERY_MS`, `ACTIVITY_THROTTLE_MS`), not of the fixture: they decide
how reading time is split into events, never how much is counted.

Ruling: Android **may** omit `session` and `view` (telemetry nothing derives from) but, if it writes them, uses
exactly these shapes — the backup remap reads `view.entryId`, and an incompatible shape would be silently kept
unremapped — cost: none for the learner.

Ruling: `read` and `journal` are written exactly as above by every client — the heatmap, the weekly summary,
goals and item 7 count them — cost if wrong: reading time or journal days differ per device.

Ruling: the web's four call sites use named payload builders in the pure module `lib/eventPayloads.ts`
(`sessionPayload()`, `viewPayload(entryId)`, `readPayload(bookId, seconds)`, `journalPayload(entryId)`), and
`payloads.json` is decoded against the builders and against the consumers (`readingPoints`, `readSeconds`,
`journalEventDue`, and the reading timer's flush) — the payload of `read` was built inline in a Svelte
component, which no fixture can reach — cost: a four-line refactor; behaviour identical.

Item 7 reconciliation: `read` = `{bookId, seconds}`, `journal` = `{entryId: string}`, verified 2026-11-17 against
what the web writes and what the server's activity rules read. "`reading-hours` sums `readSeconds`" matches the
clamping and a `read` without `bookId` still counts; "distinct `entryId` of `journal` events" means distinct
**strings**, matching the server's `distinctBy`.

## Reviews

The `review` payload is `{cardId: string, mode: <card kind>, grade: 1|2|3|4, meta?: {tier?, mistakes?, hints?,
durationMs?}}` (written by `study/events.ts`; the overview's row keeps the shape). A client reads a stored
event as a review in two steps, both pinned by `review-parse.json`:

1. **Parse** (`parseReview`): only `type: "review"`; the payload is an object with a non-empty string `cardId`
   and an integer `grade` 1–4 (`3.0` is 3; `"3"`, `2.5`, 0 and 5 are not grades), else the event is not a
   review. `mode` is kept when it is one of the six kinds `vocab`, `sentence`, `writing`, `tone`, `reverse`,
   `cloze`; missing, unknown or non-string reads as `vocab` (events from before kinds existed). `meta` is kept
   only when every present member is valid — `tier` 0, 1 or 2; `mistakes` and `hints` integers ≥ 0;
   `durationMs` a finite number ≥ 0 — else it is dropped whole (the review stays); unknown `meta` members and
   extra payload members are dropped. The envelope is kept as stored. `ts` is not read here.
2. **Validity** (`isValidReview`, the same test in `exp.ts`): `ts` parses as an instant, `cardId` a non-empty
   string, `grade` 1–4. An event whose `ts` does not parse is parsed but never counted (no replay, no XP).

An event counts as a review exactly when it parses and is valid. Replay order is `(instant of ts, id)`: the
instant, not the text (`10:00:00+01:00` and `09:00:00Z` tie and the id decides); see Order above for why the
stored whole-second copy is the one to order.

## Activity scoring (`activity.json`)

The heatmap, goals and the weekly summary read cells `{day, workspace, type, points, raw}` from
`GET /api/stats/activity` (server: `server/internal/stats/activity.go`, rules from the manifests' `activity`
members; `rules` in the fixture lists the built-in ones). A client that scores offline must give the same cells.

- Events are bucketed by the **learner day** of their stored `ts` (zone history, `study-day/`) and their
  workspace; one cell per day, workspace and type with points > 0, sorted by day, workspace, type. Types without
  a rule (`session`, `view`, `lookup`, unknown types) make no cells.
- **count** (`review`): points = raw = the number of events; the payload is not read.
- **measure** (`read`: field `seconds`, min 30, max 7200, `pointsPer` 300): the field must be a JSON number
  (integer or real), else the event is ignored; values below `min` are ignored; each event counts
  `r = min(value, max)`; points = the sum over events of `ceil(r / pointsPer)` (per event, not from the day's
  total), raw = the sum of `r`. A `read` without `bookId` counts.
- **distinct** (`journal`: `distinctBy` `entryId`): points = raw = the number of distinct JSON **string** values
  of the field that day; a number never counts.
- `raw` is what goals and the weekly summary read (seconds for `read`).

The web's per-event clamp (`stats/readingTime.ts` `readingPoints`, `readSeconds`) equals the server's for every
`read` case.
