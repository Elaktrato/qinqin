# v0.8.0 measurements (2026-11-26)

What the v0.8.0 handoff (§5) lists as unverified and a shell can measure: seed and first-boot time, sizes, memory,
endpoint latency. Everything here ran on the development machine against `feature/v0.8.0` at `05ee7410` (contract
13); nothing was drawn in a browser or run on a phone. Throw-away data directories and binaries lived outside the
repository; nothing from this run is committed except this file.

**Machine:** WSL2, 4 vCPU, 16 GB RAM (about 5 GB free during the runs), data on the WSL ext4 disk, Go 1.26, Docker
29.7. **The machine was not quiet:** other agents and Docker builds ran at times (the old-binary seed in §1.3
overlapped a Docker build). Read seconds as ± 10 %, not as benchmarks.

## 1. Seed times

Command shape (the binary was built with `go build -o <dir>/qinqin ./cmd/qinqin` from `server/`; packs read from
`plugins/data` plus the three built packs of §2.3):

```
/usr/bin/time -f "wall=%e s user=%U sys=%S maxrss=%M KB" \
  ./qinqin seed --data <fresh dir> --packs plugins/data,<kanjivg root>,<images root>
```

### 1.1 Fresh full seed

| Run | Wall | Peak RSS | DB file |
|---|---|---|---|
| All v0.8.0 packs, plus KanjiVG strokes and the two images packs | 127.0 s (user 118 s, sys 25 s) | 266 MB | 407.7 MB |
| v0.7.0 binary and v0.7.0 packs (`f58c6231`) | 119.2 s | 264 MB | 342.4 MB |
| Re-seed of the same database (nothing changed) | 91.1 s | 266 MB | |
| v0.7.0 database upgraded by the v0.8.0 binary and packs | 79.8 s | 262 MB | 407.7 MB |

The upgrade row is faster than the fresh one because the dictionaries' rows already exist. `seed` re-reads every
pack either way (an unchanged re-import writes no rows but still costs about 90 s here); the auto-seed of a running
server runs only on a fresh instance, so an existing v0.7.0 server gets the Tatoeba, KanjiVG and images packs only
through `qinqin seed` or the pack importer in the admin UI. The v0.8.0 packs cost about 10 s on top of the 119 s
baseline, inside the noise of this machine.

### 1.2 Per pack (staged runs on one database, packs added in this order)

| Pack | Wall | Peak RSS |
|---|---|---|
| dictionaries and levels (`cedict`, `jmdict`, `kanjidic2`, `unihan`, `jiten-frequency`, `hsk-*`, `jlpt-kanji`, `joyo-grades`, `tgh-chars`) in one run | 106.9 s | 257 MB |
| `ja-lemma` | 0.04 s | 29 MB |
| `ja-grammar` / `zh-grammar` | 0.11 s / 0.14 s | 39 / 43 MB |
| `kanjivg-components` | 0.12 s | 33 MB |
| **`ja-sentences-tatoeba`** (55,871 sentences) | **5.9 s** | 132 MB |
| **`zh-sentences-tatoeba`** (32,810 sentences) | **3.6 s** | 97 MB |
| **`kanjivg-strokes`** (6,614 chars) | **2.5 s** | 55 MB |
| **`images-openmoji` + `images-mulberry`** | **0.5 s** | 45 MB |
| `hanzi-writer-strokes` (9,574 chars, existing pack) | 3.6 s | 50 MB |

The sentences times include building the `sentences.<pack>` data package (format 2; 6.0 MB for ja, 4.3 MB for zh).
Deleting both package files and seeding the two packs again took 9.2 s in total, so the package build and the import
cannot be told apart at this resolution; neither is a problem. The same run of the dictionaries one pack at a time
(`cedict` 21 s, `jmdict` 48 s, `kanjidic2` 21 s, `unihan` 24 s, `jiten-frequency` 20 s) shows a fixed cost of about
20 s per dictionary-sized import, even for the 13k-entry `kanjidic2`. I did not trace the cause (the lexicon packages, 38 MB ja and 25 MB zh, are
likely rebuilt after each import, not confirmed). It is old behaviour, not v0.8.0, and fits the one-run seed being
faster than the sum of the single runs (142 s).

Not measured as such: the starter sets (embedded in the binary, 28 KB, read at serve time) and the script charts
(web data); they cost no seed time.

### 1.3 Upgrade: the v0.7.0 database

The v0.7.0 database was made with a binary built from `f58c6231` (`git archive` of `server` and `plugins`, 119 s,
above). The v0.8.0 binary then opened it (migrations 050-054 applied) and seeded the new packs: 79.8 s in total,
no errors, the sentences packages appear at `formatVersion` 2. The "format 1 to format 2 rebuild" the Tatoeba branch
describes did not occur in this run: v0.7.0 has no sentences packages, so there is nothing to rebuild; only a
database that held the earlier feature-branch builds would rebuild. Image rows are canonicalised on read (the
image endpoint answers in 1.2 ms, §4), not in a migration, so there is no upgrade step to time.

### 1.4 First boot of `serve` on an empty data directory

`QINQIN_PACKS=<all four roots> ./qinqin serve --addr 127.0.0.1:18081 --data <empty dir>`:

| Event | After start |
|---|---|
| port answering `/api/version` | **152.6 s** |
| `auto-seed: done in 2m32.2s` | 152.2 s |

The server does not listen until the auto-seed ends (existing design: `docker-compose.yml` has
`start_period: 300s` for this). With the v0.8.0 packs and the Chinese strokes pack the boot took 2m32 against the
compose file's own "about 2 minutes" comment. A host with a disk or CPU twice as slow reaches the 300 s start
period; **proposal (not implemented): raise `start_period` to 600 s, or serve a "seeding" status while the
auto-seed runs.** Peak RSS 280 MB.

## 2. Sizes

### 2.1 Repository

| | v0.7.0 (`f58c6231`) | `feature/v0.8.0` |
|---|---|---|
| tracked files | 3,265 | 3,473 |
| tracked tree, raw | 59.7 MiB | 100.4 MiB (+40.7) |
| `plugins/data` raw | 35.7 MiB | 75.3 MiB (+39.6) |
| `.git` pack of the whole history | 53.3 MB (a repack of that commit's objects) | +13.8 MB for the 71 new commits' objects |

Commands: `git ls-tree -r -l <rev>` summed with awk; `git rev-list --objects <old>..HEAD | git pack-objects --stdout
--delta-base-offset | wc -c` for the clone growth. A fresh clone therefore grows by about 14 MB (+26 %), not the
34 MiB of the handoff (that was the raw tree).

Largest new files: `ja-sentences-tatoeba/sentences.json` 16.8 MiB raw (5.0 MB gzip), `zh-sentences-tatoeba/sentences.json`
10.2 MiB (3.7 MB gzip), `ja-sentences-tatoeba/credits.tsv` 7.8 MiB (0.87 MB gzip), `zh-sentences-tatoeba/credits.tsv`
4.6 MiB (0.56 MB gzip).

**For the open `credits.tsv` question:** dropping both files would cut the raw tree by 12.4 MiB but the clone by
only about 1.4 MB (their gzip size), because git already compresses them. The saving is small in the place that
matters (clone and image download); the raw size matters only on disk and in the Docker layer (`/opt/qinqin/packs`).

### 2.2 Docker image

`docker build -t <tag> --build-arg WITH_AUDIO=0 .` (the audio stage skipped: it downloads 69 MB and is unchanged;
17 layers were cached, 80 s):

| Part | Size |
|---|---|
| image total | **343 MB** |
| Tesseract and models (existing) | 200 MB |
| `/opt/qinqin/packs` (`plugins/data`) | 78.9 MB (was about 41 MB at v0.7.0 by the tree figures) |
| `/usr/local/bin/qinqin` | 28.7 MB |
| `/opt/qinqin/strokes` (existing Chinese pack) | 12.5 MB |
| `/opt/qinqin/images` (new) | 6.7 MB compressed layer, 10.3 MB on disk |
| `/opt/qinqin/kanjivg` (new) | 7.6 MB, 7.2 MB on disk |

New in v0.8.0: about +40 MB packs, +17.5 MB images and KanjiVG, a slightly larger binary. The `images` and `kanjivg`
stages each built alone in 11-13 s.

### 2.3 What was built, and where the 56 MB download figure stands

`docker build --target images` and `--target kanjivg` both succeeded and their outputs were seeded here
(`/out` of each stage). The pinned image sources are a layer the Docker cache already held on this machine
(layer "apk add ... fetch"), so **the download time was not measured**; the `images` stage's RUN layer is 65.2 MB
(sources and output together), the output alone 10.4 MB. The 56 MB figure of the handoff is plausible against the
65 MB layer but unconfirmed. The Chinese strokes pack was built from `hanzi-writer-data@2.0.1` (`npm install` in a
scratch directory, then `node scripts/prepare-strokes-pack.mjs --out ... --source ...`) because the web stage was
not built.

## 4. API latency

Server: `./qinqin serve --addr 127.0.0.1:18080 --data <full seed>`, one user created with `qinqin adduser`, token
from `POST /api/auth/login`. Client: `curl` on the same machine, `-w '%{time_total}'`, 50 requests in a row (so
a warm cache; a loopback figure, not a network one). The script is a 10-line bash loop and sort/awk percentile.

| Request | status | median | p95 | bytes |
|---|---|---|---|---|
| `GET /api/images/entries/165346` (猫, a picture) | 200 | 1.2 ms | 1.4 ms | 2,109 |
| `GET /api/images/entries/1` (no picture) | 200 | 0.9 ms | 1.1 ms | 16 |
| `GET /hanzi/U732B.json?lang=ja` | 200 | 0.7 ms | 0.9 ms | 2,675 |
| `GET /hanzi/U732B.json` (no lang) | 200 | 0.7 ms | 0.9 ms | 2,675 |
| `GET /hanzi/U3042.json?lang=ja` (あ, KanjiVG only) | 200 | 0.6 ms | 0.8 ms | 1,770 |
| `GET /api/entries/165346` (for comparison) | 200 | 1.7 ms | 2.0 ms | 9,121 |
| `GET /api/entries/165346/examples` | 200 | 1.0 ms | 1.3 ms | 58 |
| `GET /api/packages?languages=all` | 200 | 1.8 ms | 2.5 ms | 24,668 |
| `GET /api/packages/sentences.ja-sentences-tatoeba/1` | 200 | 2.7 ms | 2.8 ms | 6,010,678 |
| `GET /api/packages/sentences.zh-sentences-tatoeba/1` | 200 | 2.4 ms | 2.7 ms | 4,322,140 |
| `GET /api/packages/strokes.kanjivg-strokes/1` | 200 | 3.0 ms | 3.5 ms | 7,926,815 |

Checks that came with it:

- With **both** stroke packs seeded, `?lang=ja` returns the KanjiVG outline of 猫 (2,675 bytes) and `?lang=zh` the
  Make Me a Hanzi one (3,363 bytes); with no `lang` the Japanese answer comes back for this character (I did not read why from the
  code). Kana (あ) exist only in KanjiVG and answer for both.
  (With only the KanjiVG pack all three requests return the same bytes, as the first run showed.)
- The catalogue lists the sentences packages with `formatVersion` 2, the other types with 1; no `images` package
  exists yet (images packs have no data package, as the handoff says).
- The "examples" answer for 猫 is 58 bytes, the empty list: that entry has no Tatoeba sentence in this dataset; it
  does not measure the per-sentence credit path. The credit link display needs an entry with a sentence.

## 5. Not measured

- Download time of the pinned image and KanjiVG sources (cached layers, §2.3); the audio stage (skipped).
- The sentences package build apart from the import (§1.2), and the format 1 to 2 rebuild (no database holds format 1).
- Latency with many concurrent clients, on a slow disk or a Raspberry Pi; the image endpoint with a cold cache after
  a restart (the first request after start was 1.2 ms, but the OS file cache was warm).
- The examples endpoint with a credit (entry without sentence used), and the sentence-package download inside the
  web app or the APK.
- Anything in a browser or on a phone (outline drawing, Write mode, Home offer, contour layout).
- A clean `docker build` with the audio stage and a cold layer cache (the full build above reused 17 cached layers).

## 6. Real problems, if any

None blocking. Two things to decide: the first-boot margin (§1.4: 152 s against a 300 s start period) and the
non-obvious fixed ~20 s per dictionary import (§1.2), which dominates a seed and predates v0.8.0.
