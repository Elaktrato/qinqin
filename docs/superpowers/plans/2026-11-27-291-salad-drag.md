# #291 — word salad: reorder tokens by drag and drop (2026-11-27)

Milestone v0.9.0, phase 2. Branch `feature/v090-291-salad-drag`, from `feature/v0.9.0` (at `814bf0f9`).

## What

The Word salad board (`lib/features/flashcards/cards/WordSaladBoard.svelte`, also the grammar practice board) only
taps: tap a bank tile to append it, tap a placed tile to send it back, Undo removes the last. A misplaced tile in the
middle means taking out everything after it. Add drag and drop (mouse, touch, pen through pointer events) and a
keyboard move, keeping tapping exactly as it is. Grading is unchanged.

## Tasks

1. This plan.
2. Pure order logic in `lib/exercises/saladOrder.ts` (test first, `saladOrder.test.ts`): `insertAt`, `moveTo`,
   `step` (one place left or right, null at the edge), `isDrag` (the movement threshold), `insertionIndex` (where a
   pointer drops into a wrapped row of tile boxes).
3. The board: pointer drag (placed tile → new position, bank tile → a position in the answer, placed tile → bank),
   the room-making gap with an insertion marker, a lifted ghost tile, Alt+←/→ on a focused placed tile, the move
   announced in a polite live region, reduced motion. DOM tests (`WordSaladBoard.dom.test.ts`): reorder by pointer, a
   bank tile dropped into the middle, a placed tile dropped on the bank, a shaky tap is still a tap, a drag is not a
   tap, Escape cancels, reorder by keyboard with the announcement, a reorder does not count as a wrong check.
4. Docs: wiki (Flashcards study sessions, Grammar lessons), `docs/releases/NEXT.md`.

## Rulings

- Ruling: the keyboard pair is **Alt+← / Alt+→** on a focused placed tile (the issue's first choice) — the study page
  ignores every key with Alt (`+page.svelte` returns on `altKey`), the hint key is H / Alt+H, so nothing clashes; the
  board calls `preventDefault`, which keeps Chrome's and Firefox's Alt+← "back" from leaving the page while a tile
  has focus — cost if wrong: a browser that reserves Alt+← (none of the targets) would navigate back; the tap path
  still works.
- Ruling: arrows follow the screen, not the reading order: in a right-to-left layout Alt+← moves toward the end — no
  study language is right-to-left today; it costs one line — cost if wrong: nothing visible now.
- Ruling: the drag threshold is **8 px** for mouse and pen and **10 px** for touch — a finger's tap wanders a few
  pixels, 10 px is the usual "touch slop"; below it the release is a tap and does exactly what tapping does today —
  cost if wrong: a slow, deliberate drag needs a couple more pixels before it lifts.
- Ruling: tiles get `touch-action: none` — without it the browser (and the Android WebView) takes a finger's move
  on a tile as a scroll and sends `pointercancel`; the page still scrolls from everywhere else on the card — cost if
  wrong: a learner who starts a scroll on a tile moves the tile instead (it lands back where it was when released
  off the rows).
- Ruling: once a drag starts, the pointer is captured by the board itself (not the tile) — the dragged tile leaves
  the row while the others close up and the marker opens a gap; capture on a node that leaves the DOM would be lost.
  It also means the release's `click` goes to the board, so a drag never also taps — cost if wrong: none seen; a
  defensive flag ignores the one click that could still follow a drag.
- Ruling: the drop target is the answer row (and a band of 24 px around it) or the bank; a release anywhere else
  puts the tile back where it came from — dropping "nowhere" should change nothing — cost if wrong: a tile dropped
  just past the band returns instead of landing at the nearest end.
- Ruling: the insertion index is worked out from the live boxes of the other tiles (the line the pointer is on, then
  the tiles of that line whose centre is before the pointer) and the gap is the size of the dragged tile — with a
  tile-sized gap the index is stable as the pointer crosses a centre (the classic sortable list), no cached layout
  is needed — cost if wrong: at the end of a wrapped line the gap can flip between the two lines.
- Ruling: the lifted tile under a finger sits **above** the touch point (its bottom 12 px above the finger); a mouse
  or pen keeps the grab offset — the issue asks that the finger does not cover it — cost if wrong: cosmetic.
- Ruling: no sliding animation of the tiles; only the gap grows in (a 120 ms width animation), none with
  `prefers-reduced-motion: reduce` — the app has no list animations (`animate:`) and jsdom has no Web Animations; a
  CSS keyframe on the gap is enough to show room being made — cost if wrong: tiles jump rather than slide also with
  motion on.
- Ruling: the Android **system** back gesture (an edge swipe) cannot be blocked from a web page; the board keeps its
  tiles inside the card's gutters and `touch-action: none` stops the WebView's own scrolling and overscroll. Checking
  it on a phone is a local follow-up — cost if wrong: a drag that starts within the system's edge zone goes back; the
  owner then asks for `setSystemGestureExclusionRects` in the shell (a native change).
- Ruling: a move by keyboard or pointer is announced as "食べ moved to position 3 of 5" (new string
  `flashcards.salad.moved`), a bank tile dropped into the row likewise, a tile dropped on the bank as
  "食べ removed" (`flashcards.salad.removed`) — the existing feedback line stays for Check results; the announcement
  is a separate visually hidden polite region so it does not erase the Check feedback — cost if wrong: two strings.
